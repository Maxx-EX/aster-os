# 架构说明

## 1. 为什么分成引导器和内核两级

单级内核（把校验写进内核自己）有个死结：校验代码和被校验对象在同一块内存里，改镜像的人可以顺手把校验逻辑一起改掉。

所以采用两级：

- **引导器**只做四件事：初始化串口、校验、加载、跳转。代码量压到 12 KiB，容易审计。
- **内核**不持有密钥，只能"复算并比对"，不能"自己签发"。

密钥 K 只存在于 `boot/manifest.h`（构建时由 `tools/aster-sign.py` 从 `boot/keys/boot.key` 注入），编译进引导器的只读段。内核链接的 `libaster_c.a` 里没有 K。

## 2. 启动时序

| 步骤 | 位置 | 关键点 |
| --- | --- | --- |
| 0 | QEMU `-kernel` | 载入 ELF，从 `_start` 进 EL1，MMU/cache 关闭，x0 = DTB |
| 1 | `boot/start.S` | 只留 0 核；设栈；清 bss；`CPACR_EL1.FPEN=0b11` |
| 2 | `boot/main.c` | `uart_init` → banner → `avp_check` |
| 3 | `boot/verify.c` | 三级校验，详见 verify-chain.md |
| 4 | `boot/main.c` | 可信 → 3 秒菜单；不可信 → 直接 `shell_run` |
| 5 | `boot/image.c` | 逐字节拷到 `0x4020_0000`，`dc cvau` + `ic ialluis` |
| 6 | `boot/image.c` | `br x1`，x0 指向 `struct aster_bootinfo` |
| 7 | `kernel/src/boot.S` | 设内核栈、放行 FP、清内核 bss |
| 8 | `kernel_main` | 校验 magic → 装异常向量 → 复算摘要 → **比对 EX3** → 开 MMU → shell |

### 为什么 FP/SIMD 要显式放行

`CPACR_EL1` 默认把 EL1 的 FP/SIMD 访问 trap 掉。Rust 编译器生成的代码会用到 NEON（复制、清零都会），一旦没放行，第一条 NEON 指令就触发 `EC=0x07`。

第一次跑内核就是死在这里，异常现场打出来是 `ESR=0x1fe00000 / ELR=0x40201180`。修复就是入口处 `msr cpacr_el1, #0x300000`。

## 3. 内存与 MMU

QEMU virt 的 RAM 从 `0x4000_0000` 开始。引导器把自己放在 `0x4008_0000`，内核放 `0x4020_0000`，中间留出 1.5 MiB 给引导器自身（含内嵌镜像）和栈。

MMU 用 4 KiB 粒度、39 位 VA、恒等映射。阶段一只有 L1 的 1 GiB 块，阶段二为了能单独给用户段开权限，把 RAM 那一段拆成了三级：

```
L1[0]       0 - 1 GiB    Device-nGnRnE   AP=EL1RW  UXN=1
L1[1]   →   L2（1 - 2 GiB，QEMU 的 RAM 在这里）
  L2[i]     每项 2 MiB  Normal WBWA      AP=EL1RW  UXN=1    ← 内核
  L2[34] →  L3（0x4440_0000 起的 2 MiB）
    L3[0]   用户代码页 4 KiB             AP=EL0RW  UXN=0    ← EL0 可执行
    L3[1]   guard 页（不映射）           ——                 ← 越界立刻 fault
    L3[2]   用户栈页 4 KiB               AP=EL0RW  UXN=1    ← 可读写、不可执行
L1[2], L1[3] 2 - 4 GiB   Normal         AP=EL1RW  UXN=1    （预留）
```

描述符字段：`bit[1:0]=0b01` 块 / `0b11` 页（L3）/ `0b11` 表（指向下一级）；`AP[7:6]`；`SH[9:8]=0b11`；`AF=1`；`PXN[53]`、`UXN[54]`。

> 关键在于 `AP=0b00` 的内核页：EL0 就算拿着 `0x4020_0000` 也读不到任何一个字节 —— 这是页表硬件拦的，不是软件 `if` 拦的。`runf` 命令就是专门验证这一点。

> 另一个坑：`SCTLR_EL1.SPAN(bit23)` 默认是 1，异常进入 EL1 时会自动置 `PSTATE.PAN`，那样内核在 syscall 里读用户 buf 会直接 fault。cortex-a72 属于 ARMv8.0，PAN 是 v8.1 的可选特性，这一版把 SPAN 清 0，用户内存的访问控制交给页表 AP 位 + `user_ptr_ok` 软件校验。

> 踩过的坑：一开始把 `bit[1:0]` 写成 `0b11`，那是**表描述符**，硬件会把高 48 位当成下一级表地址去翻译，立刻挂死且没有异常输出。块描述符必须是 `0b01`。

`MAIR_EL1 = 0xFF | (0x04 << 8)`：attr0 普通内存、attr1 Device-nGnRnE。

## 4. 异常

`exceptions.rs` 用 `global_asm!` 造 16 项向量表（每项 128 字节），按来源分流：

```
0-3    Current EL with SP_EL0    → aster_unexpected（内核自己不用 SP_EL0，兜底）
4-7    Current EL with SP_ELx    → aster_unexpected（内核态崩了：打印现场后停机）
8-11   Lower EL using AArch64    → 8 号槽 = aster_svc_entry，其余兜底
12-15  Lower EL using AArch32    → aster_unexpected
```

EL0 的 `svc`、data abort、非法指令**都落在 8 号槽**，所以 `svc_entry` 里先看 `ESR.EC`：

- `EC=0x15` → 系统调用，按 `x8` 分发
- 其它 → 用户态故障：打印 EC/ELR/FAR，杀掉这个任务，**内核继续活着**

`VBAR_EL1` 在 `chain_check` 之前就装好，所以后面任何一步崩都有输出。

## 5. 内核里的 Rust / C 分工

- Rust：内存布局、MMU 页表、异常、命令行、字符串处理 —— 这些地方值得用类型系统兜住
- C：`sha256.c`（与引导器**同一份源码**，保证两侧摘要一致）、`aster_c_hash_image` / `aster_c_ct_eq` 两个薄封装

同一个 SHA-256 实现被编译两次（引导器和内核），这是故意的：链式校验的意义就在于"两边独立算、结果必须相同"。如果共用同一份运行时状态，就等于自己验自己。

`build.rs` 在构建时调 `aarch64-linux-gnu-gcc` 编 C 再 `ar` 成 `libaster_c.a`，由 `cargo:rustc-link-lib=static=aster_c` 交给 rust-lld。

## 6. EX3 落到代码里的位置

`EX3` 不是一个手写常量，而是构建产物：

| 环节 | 文件 | 说明 |
| --- | --- | --- |
| 生成 | `tools/aster-sign.py gen-ex3` | `HMAC(K, BOOT_ID‖"EX3"‖build_id‖nonce)` |
| C 侧载体 | `boot/ex3.h`（生成） | `ASTER_EX3[32]`、`ASTER_EX3_TAG` |
| Rust 侧载体 | `kernel/src/ex3.rs`（生成） | `EX3: [u8;32]`、`EX3_TAG` |
| 传递 | `bootinfo.ex3` | 引导器校验通过后填进 bootinfo 交给内核 |
| 比对 | `kernel_main` → `ex3_check` | 32 字节常量时间比较，不一致就 wfe 停机 |

两个生成文件都在 `.gitignore` 里：克隆下来的人第一次 `make` 会用自己的 K 和 nonce 生成属于自己的 EX3，不会和仓库里某人构建出的值撞车。

## 7. 串口协议之外的东西

引导器里还有个 `AFP`（Aster Flash Protocol），跑在串口上：握手 → 长度 → 期望 MAC → 数据。收到数据后用同一把 K 算 HMAC 比对，通过了才标记为"可信暂存镜像"，`boot` 命令就会优先从暂存区启动。

协议细节见 `boot/flash.c` 顶部注释，主机端实现 `tools/afp-flash.py`。

## 8. 用户态与系统调用

### 用户程序不是内核的一部分

`user/hello.S` 用交叉汇编编出来，链接到 `0x4440_0000`，`objcopy -O binary` 得到一个几百字节的扁平镜像，再由 `kernel/build.rs` 编成 Rust 静态数组嵌进内核。内核启动时它只是一段数据，`run` 命令才把它拷进用户代码页。

这样做的原因：阶段二还没有文件系统，也没有 ELF 加载器。等有了块设备驱动，同样的 `load_user_image(binary)` 接口可以换成"从盘上读 ELF、按段映射"，内核内部逻辑不用动。

### 切到 EL0 的三步

```asm
aster_enter_user:            // x0 = 入口, x1 = 用户栈顶
    adr  x2, ASTER_USER_CTX  // 先把内核自己的现场存起来
    ...                      // [0]=sp, [1..12]=x19..x30, [13]=退出码
    msr  sp_el0, x1          // 用户态用它自己的栈
    msr  elr_el1, x0         // 返回地址 = 用户入口
    msr  spsr_el1, xzr       // M=EL0t、DAIF 全开
    .irp r, 0,1,...,30
    mov  x\r, xzr            // 清空所有通用寄存器，不留内核残留
    .endr
    eret
```

`eret` 之后 CPU 就在 EL0 跑用户代码，任何 `msr/mrs` 特权指令、任何对外设的访问都会 trap。

### 系统调用的现场

`svc #0` 进 8 号槽，`svc_entry` 先在内核栈上压一个 160 字节的陷阱帧：

```
[sp,#0]    x0 x1     ← 系统调用参数；返回值也写回这里
[sp,#16]   x2 x3
...
[sp,#64]   x8 x9     ← x8 = 系统调用号
...
[sp,#144]  x18 x30
```

`svc_handler(esr, elr, frame)` 读 `frame[8]` 拿调用号，处理完把返回值写进 `frame[0]`；汇编恢复现场后 `eret`，用户就在 `x0` 里拿到结果。

退出（`exit` / 用户态故障）走另一条路：`svc_handler` 返回 1，`svc_entry` 跳到 `aster_task_exit`，丢掉陷阱帧、从 `ASTER_USER_CTX` 恢复内核的 sp 与 x19–x30，`ret` 回 Rust 调用点，`x0` 是退出码。shell 于是打印 "用户任务已退出，退出码 = 7"。

### 系统调用号

沿用 AArch64 Linux 的编号，为以后能直接跑现成的用户态程序（APK 的 bionic 层也认这套）留路：

| 号 | 名称 | 参数 | 返回 |
| --- | --- | --- | --- |
| 64 | write | fd, buf, len | 写入字节数 / `-EBADF` / `-EFAULT` |
| 93 | exit | code | 不返回 |
| 172 | getpid | — | 1 |

`buf` 必须落在用户代码页或用户栈页内（`mmu::user_ptr_ok` 检查起止），否则返回 `-EFAULT`。哪怕页表权限配错，用户也没法借 `write` 把内核内存读出来。

### 踩过的两个坑

1. **ELR 不需要 +4**。AArch64 的 `SVC` 保存的 `ELR_EL1` 已经是"下一条指令"的地址（和 x86 的 `int` 不同）。一开始按 x86 直觉加了 4，结果用户程序每次被跳过一条指令：`mov x8,#9999`、`mov x0,#7` 全没执行，参数一路滞后一轮，表现为"第 4 次调用打印的却是第 3 次的参数"。
2. **退出码槽和 x30 槽撞了**。`ASTER_USER_CTX` 里 `x19..x30` 是 12 个寄存器（索引 1..12），退出码必须放索引 13。一开始放 12，把 x30 覆盖成返回值，`ret` 直接跳到 `-9` 地址，报 `Data Abort`。

### 隔离验证

`runf` 装载 `user/fault.S`，它执行 `ldr x1, [0x40200000]`（内核镜像基址）。实测输出：

```
!!! 用户态故障（Aster 捕获，内核继续运行）!!!
  EC      = 0x24 (数据中止(低 EL))
  ELR     = 0x0000000044400004  (出错指令)
  FAR     = 0x0000000040200000  (访问地址)
  → 该任务被终止，返回内核 shell。
```

`EC=0x24` 就是 "Data Abort from a lower Exception level"，也就是硬件认定 EL0 越权。内核没有停机，回到 `aster>` 继续可用。

## 9. 中断、定时器与抢占

### 一条完整的中断链路

```
CNTP_TVAL 到期 → PPI 30 → GICv2（GICD 0x0800_0000 / GICC 0x0801_0000）
   → CPU 在 EL0 时 IRQ 不被屏蔽 → 向量表 9 号槽 aster_lower_irq
   → SAVE_FRAME（272 字节） → irq_handler → sched::tick(frame) → LOAD_FRAME → eret
```

`irq_handler` 的顺序是固定的：`ack()` 取中断号 → `timer::disarm()` 清掉本次 → `timer::arm()` 装下一次 → `tick()` 换人 → `eoi()`。先 disarm 再 arm 是必须的，否则定时器的中断线还拉高，`eoi` 之后会立刻再进一次，变成中断风暴。

`ack()` 返回 1023 是 spurious，直接返回且**不写 EOIR** —— 对伪中断写 EOIR 在 GICv2 上是未定义行为。

### 为什么所有异常共用一个陷阱帧

如果 IRQ 抢占另写一套保存/恢复，SVC 和 IRQ 就会有两份寄存器布局，改一处忘一处。这里统一成 34 个 u64：

```
[0..30]  x0..x30        [31] SP_EL0        [32] ELR_EL1        [33] SPSR_EL1
```

调度器的工作因此简化成一句话：**把当前帧存进 `Task.ctx`，把下一个任务的 `ctx` 覆盖到同一帧上**。`eret` 出去时 CPU 已经在跑另一个任务，不需要额外的"任务切换汇编"。任务第一次运行也是同一个帧——只是 `ctx` 由 `spawn()` 预先填好。

### 抢占的证据

`runp` 把任务 A 设成纯计算（1.3 亿次减法，中间一次 `svc` 都不发），任务 B 是打印任务：

```
BUSY start
TASK 2
TASK 2
...（30 行）
[SVC] exit(0)  ← 任务 2
BUSY end
[SVC] exit(0)  ← 任务 1
```

B 的 30 行全部落在 A 的 `BUSY start` 和 `BUSY end` 之间，而且 B 还正常退出了。这说明 A 在长时间独占 CPU 意图时，定时器照样把 CPU 抢给了 B。如果换成没有抢占的系统，这 30 行会全部排在 `BUSY end` 之后 —— 也就是"一个失控程序锁死整机"。

`make test` 里用 awk 断言了这个行序关系，不是靠肉眼看日志。

### 这一版调度器的边界

| 有 | 没有 |
| --- | --- |
| 2 ms 时间片、round-robin | 优先级、阻塞/唤醒、睡眠 |
| 每任务独立用户代码页与栈（不同虚拟区间） | 每任务独立 TTBR0 页表（任务间能互读对方页） |
| 任务越权 → 杀任务、内核继续 | 每任务独立内核栈 |
| 退出码回传、切换计数 | 浮点/NEON 上下文保存（帧里没有 Q0-Q31） |

最后一条是实际隐患：用户程序只要用一次 NEON，被抢占后寄存器组就会串。当前 `hello` / `busy` / `fault` 都是纯整数代码，所以跑得对；但这是一个早晚要补的洞，已写进 `docs/roadmap.md`。

### 中断期间不能做的事

- 内核态（EL1）**全程屏蔽 IRQ**（进入异常时硬件自动置 DAIF）。所以 `svc_handler`、`println`、UART 输出都不会被抢占打断，这也意味着这些路径里不能写死循环。
- `irq_handler` 里不做任何打印：UART 输出要花时间，在中断里做会拖长关中断窗口。

## 10. 图形输出与远程访问

### 10.1 为什么是 ramfb

QEMU 的 `virt` 机器上没有 PCI 显卡（除非手动挂 virtio-gpu），但有一个更简单的设备：**ramfb**。它不是显卡，只是一块由固件接口描述的线性帧缓冲——guest 把自己的内存地址、分辨率、像素格式写进 `fw_cfg` 的 `etc/ramfb` 条目，QEMU 就把那块内存当作屏幕内容显示出来。对内核来说，画图就是往一段内存里写 `u32`。

代价是要先会跟 `fw_cfg` 打交道，而这一层在 6.2 版本的 QEMU 上坑不少（见 10.3）。

### 10.2 三层接口

```
内核 fb 模块
  │
  ├── fw_cfg 目录：找 "etc/ramfb" → 拿到它的 selector
  ├── fw_cfg 读：DMA 读 28 字节配置
  └── fw_cfg 写：DMA 写回 28 字节配置（addr / fourcc / flags / w / h / stride）
```

`fw_cfg` 的 MMIO 地址在 `0x0902_0000`（DTB 里写作 `fw-cfg@9020000`）：

- `+0x00` data 寄存器，8 字节，只接受 8 字节对齐访问
- `+0x08` selector 寄存器，2 字节
- `+0x10` DMA 地址寄存器，8 字节

DMA 描述符 16 字节：`{ u32 control; u32 length; u64 address; }`，字段**大端**。`control` 位定义：`bit0`=error、`bit1`=read、`bit2`=skip、`bit3`=select、`bit4`=write。写完描述符后把它的物理地址写进 `+0x10`，QEMU 自己填缓冲区，`bit0` 清零表示完成。

### 10.3 四个踩过的坑（都真实发生过）

1. **selector 要预反转**。设备按"大端设备"建模，AArch64 侧是小端访问，QEMU 会把写入值再按大端反转一次。直接写 `0x0022` 到设备那侧变成 `0x2200`，选不中任何条目。正确做法是 `key.to_be()` 先反转，抵消设备的反转。
2. **文件目录的 key 是 `0x0019`，不是 `0x0022`**。`0x0022` 是目录里某个文件项的 selector，选它会读到别的东西（当初读到一段 `RSD TPR ` 的垃圾）。用 `-trace "fw_cfg*"` 能看到 QEMU 自己打印的 `fw_cfg_add_bytes key 0x0019 'file_dir'`。
3. **8 字节 MMIO 读和多字段结构会错位**。目录是 `u32 count` + 每项 64 字节（`u32 size | u16 select | u16 reserved | char name[56]`），用 8 字节块一块块读，很容易和内部游标对不上。改成 DMA 整块搬 2052 字节后一次就对。
4. **ramfb 配置字段要大端**。fw_cfg 的写回调交给设备的值按大端解释，配置里 `addr=0x5000_0000` 若按小端写，设备收到的是 `0x0000005000000000`，屏幕就一直停在 "Guest has not initialized the display (yet)"。

另外 `fw_cfg` 目录里的字段本身也是大端（QEMU 用 `cpu_to_be32` 写进去的），只有一个缓冲里混着"大端字段"和"原样字节流"两种东西，读的时候要分开对待。

### 10.4 framebuffer 与绘图

- 物理地址 `0x5000_0000`（512 MiB RAM 的高段，避开内核、用户槽和 AFP 暂存区）
- 1024×768，`XRGB8888`，stride 4096 字节，共 3 MiB

绘图只有四个原语：`fill_rect`、`frame_rect`、`clear`、`draw_glyph`。上层 `draw_text` 按字符分流：ASCII 走 8×16 点阵，汉字走 16×16 点阵，宽度按 8/16 递进，所以中英文能混排在同一行。

字模不是手写的，是 `tools/genfont.py` 用系统字体渲染出来的：

```bash
python3 tools/genfont.py     # 生成 kernel/src/font.rs（ASCII 95 + 汉字 74）
```

只生成界面上真正用到的汉字（`CJK_CHARS` 列表），一个汉字 32 字节，74 个才 2.4 KiB。想加字就往那个字符串里加一个字，重跑脚本、重编内核。

### 10.5 远程链路

```
                    ┌─────────────┐
   手机 VNC 客户端 ──►│  QEMU :5901 │──► ramfb（内核写的帧缓冲）
                    │             │
   手机/电脑 nc    ──►│  QEMU :4444 │──► PL011 UART（引导器/内核命令行）
                    └─────────────┘
```

要说清楚边界：**网络协议栈不在 Aster 内核里**。现在的"远程"是 QEMU 在宿主侧把串口和显示转成 TCP / VNC，内核自己仍然只会写 UART 和帧缓冲。内核里跑 TCP/IP、跑 SSH，那是后面阶段的事。

`make run-gfx` 用 `-display vnc=0.0.0.0:1` 和 `-serial tcp:0.0.0.0:4444,server,nowait` 启动；`make shot` 则用 monitor 的 `screendump` 抓 PPM 再转 PNG，用于无头验证。

### 10.6 这一块还没做的

- 鼠标：键盘已经有了（见 §12），鼠标还没有，窗口拖不动、点不了
- 多窗口 / 合成器：现在是"单窗口桌面"，没有真正的窗口管理器
- 面板不是"实时"的：`run` 期间 shell 被阻塞在任务循环里，界面要等命令回来再按 `gfx` 重绘，所以任务表反映的是"上一次运行之后"的状态，不是运行中。EL1 期间的中断走 5 号槽，不触发调度（见 §9）

## 11. 网络

### 11.1 为什么又选了 virtio-mmio

上一节为了图形绕开 PCI，这次也一样。`virt` 机器把 32 个 virtio-mmio 槽摆在 `0x0a000000` 起、每槽 `0x200` 字节，设备倒序分配（第一个挂上的在第 31 槽，即 `0x0a003e00`）。走 mmio 的好处是不用 ECAM 枚举、不用 BAR 映射、不用 MSI-X，坏处是**没有 PCI 的 capability 描述**，版本行为完全依赖设备。

### 11.2 那个让人误判一整晚的 legacy 坑

QEMU 6.2 的 virtio-mmio 默认 `force-legacy=1`，于是设备自报 `Version=1`。按 legacy 规范写：

```
QueueSel=0 → QueueNum=8 → QueueAlign=4096 → QueuePFN=mem>>12 → Status|=DRIVER_OK → QueueNotify=0
```

全部写进去，寄存器读回也全对，`Status=0x7`（ACK|DRIVER|DRIVER_OK），`InterruptStatus=0`，**但 `used.idx` 永远是 0**。表现为：

- 驱动初始化"成功"，MAC 从 config 空间读得到（`52:54:00:12:34:56`）
- RX 挂了 8 个缓冲（`avail.idx=8`）
- 收发计数 `0/0`，宿主 `curl` 12 秒超时 `HTTP 000`
- `-trace "virtio*"` 显示 690 万次读、16 次写，`0x50` notify 确实到达了设备

也就是说：设备收了 notify、认了 DRIVER_OK，却从不消费描述符。试过把 `QueuePFN` 先清 0 再设、把 QSIZE 换成 64、确认 desc 页对齐与物理可达——都没用。

**解法**：加 `-global virtio-mmio.force-legacy=false`，设备变成 `Version=2`，走 modern 队列寄存器（`QueueDescLow/High`、`QueueDriverLow/High`、`QueueDeviceLow/High` + `QueueReady=1`）。同一份驱动逻辑立刻正常：`curl` 拿到 `200`，收发计数立刻动起来。

代码里两条路径都保留了（`virtio::setup_queue_legacy` / `setup_queue`），但**默认启动一律 modern**，`make run-net` / `tools/nettest.py` 都带这个参数。

### 11.3 队列与内存布局

RX 与 TX 各一块 8 KiB 的页对齐静态区（`#[repr(C, align(4096))]`），内部切成 desc（`8×16=128`）、avail（紧跟其后）、used（固定在偏移 4096）。QSIZE=8，每帧缓冲 2048 字节，RX 用 `DESC_F_WRITE`，TX 用 `DESC_F_NEXT` 串两段（virtio-net 头 + 帧体）。

`VIRTIO_NET_F_MRG_RXBUF` 与 `VIRTIO_NET_F_MAC` 参与协商；`HDR_LEN=12`（协商了 MRG 时头是 12 字节，没协商是 10）。

### 11.4 协议栈是自己写的

按依赖顺序实现，每步都能在串口里看到证据：

1. **ARP**：开机先广播三次 `who has 10.0.2.2`。这一步不是可选的——slirp 只有在收到 guest 的帧之后才学到"这个 IP 对应这个 MAC"，在此之前它拿到宿主侧连接也没有目的地址可填，SYN 根本送不下来。少了这三次喊话，现象同样是"收帧 0"。
2. **ICMP**：应答 echo，验证链路。
3. **TCP**：三次握手、序号/确认号、ACK、FIN、单连接。校验和按 RFC 1071 反码求和。
4. **HTTP/1.1**：解析请求行与方法，返回编译进镜像的中文页面（`HTTP_PAGE` 用 `r#""#` 原样串，因为 HTML 里有 `#`）。

驱动层与协议层之间只有两个函数：`send_frame(&[u8])` 和轮询 `pop_used()`。`net::poll()` 挂在 shell 的空闲循环里，所以只要系统在等输入，网络就在收包。

### 11.5 边界

- 没有重传、没有滑动窗口、没有乱序处理；丢了就丢了
- 没有 UDP / DNS / DHCP（地址是写死的 `10.0.2.15`，slirp 的固定网段）
- 没有 TLS
- 一次只维护一条连接，`建立连接` 计数只增不减（不复用端口）
- 端口从宿主进 guest 仍需 QEMU `hostfwd`，因为 guest 在 NAT 后面

## 12. 输入设备与桌面

### 12.1 事件模型

`virtio-keyboard-device`（DeviceID 18）只有一条队列：queue 0 = eventq，方向"设备→驱动"。每个事件 8 字节、全部小端：

```
u16 type  0=EV_SYN  1=EV_KEY  2=EV_REL
u16 code  Linux 键码（30='a'、42=LShift、58=CapsLock…）
u32 value 1=按下 0=抬起 2=自动重复
```

挂 8 个 8 字节缓冲，消费一个立刻归还并 `notify(0)`——**不归还就会在敲十几个键之后彻底卡住**，因为队列只有 8 格。

### 12.2 键码到字符

`key_to_char` 是一张 `Linux code → (无 Shift, 有 Shift)` 的表：字母走大小写映射，符号（`1`↔`!`、`[`↔`{`）走 Shift 分支。`CapsLock` 只影响字母，`Shift` 与 `CapsLock` 用异或合成。`Enter/Backspace/Tab/Esc` 翻译成 `\n / 0x08 / \t / 0x1B`，其余丢弃。

字符进一个 128 字节的环形缓冲。`shell::read_line` 的循环变成三路：**先取键盘环，再取串口，都没有就自旋**。这样键盘和串口可以同时用，谁先到算谁的。

### 12.3 屏幕终端与重绘节流

串口输出与屏幕共用一份内容：`uart::puts()` 在写 PL011 之前先 `term::write(s)`。终端缓冲是 `26×88` 个 `u16`：

- `0` = 空
- `<0x80` = ASCII
- 其它 = Unicode 码位
- `0xFFFF` = "宽字符第二格"——汉字占两格，保证中英混排行列对齐

全屏重绘一次约几十毫秒（1024×768 的填充 + 2288 个格子的字模），所以不按帧刷：`term` 写入时置脏标记，`ui::tick()` 在 shell 等待输入的空闲里检查，**脏 + 距上次 ≥60 ms** 才重画。

### 12.4 布局与配色

1024×768，深色系：

| 区域 | 位置 | 内容 |
|---|---|---|
| 顶栏 | y=0..28 | `ASTER 星芒 v0.5 ARM64 原创内核` + 右 `EX3-…` 短指纹 |
| 图标列 | x=24，y=76 起 | 终端 / 系统 / 网络 / 关于（入口占位） |
| 主窗口 | 140,60 848×600 | 标题栏（终端 TERMINAL + 三键）+ 终端内容 |
| 任务栏 | y=720..768 | 开始按钮、运行中程序（下方亮条）、键盘/网络状态灯、运行时长 |

壁纸用 48 条横带做的纵向渐变（`lerp(0x101a26 → 0x1d3149)`），右上两块微亮矩形打破平板感。强调色 `#4FC3F7`（青）、状态绿 `#7EE787`、警示橙 `#FFB86B`。

字模来自 `tools/genfont.py`：ASCII 8×16（DejaVuSansMono-Bold），汉字 16×16（arphic `uming.ttc`）。**字表按源码自动提取**——脚本扫 `kernel/src/*.rs` 里所有非 ASCII 字符，去重后写进 `CJK_CHARS`，当前 641 个汉字，随文案更新自动增减。

### 12.5 还没做的

- 鼠标与光标
- 窗口管理与多窗口
- 多终端会话（现在串口与屏幕是同一份流）

## 13. 页帧分配器与每任务地址空间

阶段二收口的前两步：#5 页帧分配、#4 每任务独立页表。这两个必须一起做——独立页表要动态申请页表页，没有分配器就只能继续写死地址。

### 13.1 池子划在哪

```
0x4008_0000  引导器（Aster Boot）
0x4020_0000  内核镜像
0x4440_0000  旧用户槽（兼容路径，保留）
0x4800_0000 ─┐
             │ 页帧池 128 MiB / 32768 页
0x5000_0000 ─┘
0x5000_0000  framebuffer（ramfb，3 MiB）
```

池子上下界都是硬边界，不是"大概":下界避开内核与旧槽，上界**正好卡在 framebuffer 起点**——把显存借出去当普通页用，画面会立刻花掉，这种 bug极难查。

### 13.2 位图与清零

`frame.rs` 用 512 个 `u64` 管 32768 页，1 = 已占用。两条不变量：

1. **分配即清零**。新任务的栈页如果留着上一个任务的栈内容，隔离就是纸面上的——任务 B 能从自己的栈里读到 A 的局部变量。
2. **越界即拒**。`free()` 检查地址落在池内且页对齐，否则直接返回；不信任调用方。

`alloc_pages(n)` 做连续分配（线性扫第一个 n 页的空洞），给将来 DMA 缓冲留着。

### 13.3 一个地址空间 = 5 页

```
L1（512 项）  复制内核 L1；L1[1] 指向自己的 L2
L2（512 项）  复制内核 L2（512 个 2 MiB 块）；只有覆盖 0x4440_0000 的那一项改指自己的 L3
L3（512 项）  [0] code  AP=EL0RW UXN=0    [1] 不映射（guard）   [2] stack AP=EL0RW UXN=1
code 页 / stack 页
```

关键设计：**所有任务用同一段虚拟地址**（`0x4440_0000` 代码、`0x4440_2000` 栈），但 L3 指向各自的物理页。好处是用户程序链接地址不用变、`ELR_EL1` 不用改、`user_ptr_ok` 的范围检查照旧；隔离完全由"换 TTBR0"这一个动作完成。

代价是每任务固定 5 页（20 KiB），且任务切换必须刷 TLB（没用 ASID）。

### 13.4 什么时候换页表

三处，缺一不可：

1. **定时器 tick**（`sched::load_into`）：切任务前先 `mmu::activate(space)`，否则返回 EL0 的第一条指令还在旧地址空间里取。
2. **任务退出**（`sched::exit_current` 无后续任务时）：切回内核页表，否则 shell 在内核里跑着跑着用的是某个死任务的页表。
3. **进入 EL0 之前**（`task::run_*`）：首任务还没被 tick 切过，得手动激活。

中断里换 TTBR0 是安全的，因为**内核代码在每张页表里都映射**（L1[1] 与 L2 是复制过去的）——换完继续执行中断收尾代码不会缺页。

### 13.5 隔离证据

`iso` 命令（`user/iso.S`）：两个任务跑同一份代码，各自往**同一个虚拟地址** `0x4440_0800` 写不同魔数，忙等约 16 ms（足够被抢占几次），再读回。

```
ISO 1: .
ISO 2: .
```

两个点 = 各自读到自己的值。如果共用一张页表，后写的会覆盖先写的，必然至少出现一个 `X`。这条断言已进 `make test`。

### 13.6 还没做的

- **ASID**：每次切换 `tlbi vmalle1is` 刷全 TLB，任务多了会明显变慢。TCR_EL1 的 AS 位 + TTBR0 的 ASID 字段是现成的解法。
- **共享页**：没有共享内存机制（将来 fork 的 COW、共享库都要）。
- **按需分页**：所有页在创建时就分配，没有缺页处理（`EC=0x24` 在用户态只是报错）。
- **栈自动增长**：栈固定在 1 页，溢出会撞 guard 页而不是自动扩。

## 14. 浮点与 NEON 上下文

### 14.1 只存 x0–x30 是不够的

陷阱帧原来只有 272 字节（31 个通用寄存器 + SP_EL0 + ELR + SPSR）。这在纯整数程序里够用，但只要任务用 `d0`/`q0` 做浮点，被时间片打断后换回来，寄存器早就属于别人了。

证据就是 `user/fp.S`：两个任务各把 `d0` 设成 1.5 和 2.5，忙等 16 ms（必然被抢占若干次），再比较自己的值。帧里不存 `q0–q31` 的话，这段程序会稳定打印 `X`。

### 14.2 新帧布局（800 字节）

| 偏移 | 内容 |
|---|---|
| 0–272 | x0–x30、SP_EL0、ELR_EL1、SPSR_EL1（原样） |
| 272–784 | q0–q31（512 字节，每对 32 字节一条 `stp`） |
| 784 | FPSR |
| 792 | FPCR |

`FRAME_WORDS` 从 34 变 100，调度器仍然只做"整块拷贝"——帧变宽了，代码一行没改。

### 14.3 一个汇编细节

`stp q0, q1, [sp, #784]` 编不过：`STP` 的立即数是 7 位、按 16 缩放，范围只有 ±512 字节。所以先 `add x0, sp, #272` 把基址挪进去，再用 `[x0, #0] … [x0, #480]` 写。用 `x0` 当临时是安全的——它此刻已经存进 `[sp, #0]` 了。

恢复顺序也有讲究：先把 ELR/SPSR/SP_EL0 装上，再恢复 `q0–q31` 与 FPSR/FPCR，**最后**才 `ldp x0, x1, [sp, #0]` 恢复通用寄存器——因为 `x1` 全程当临时基址用。

### 14.4 内核自己也会用浮点

Rust 编译出来的内核代码会用 SIMD 做拷贝，这会覆盖 `q` 寄存器。但保存发生在**异常入口的第一时间**（`SAVE_FRAME` 在调用任何 Rust 函数之前），所以内核后续怎么用都不影响已经落栈的那份。恢复时再从栈上读回来。

### 14.5 证据

```
[FP] 两个任务各持一个 d0（1.5 / 2.5），被抢占后比较：'.' = 没串，'X' = 串了
FP 1: .
FP 2: .
```

已进 `make test`（第 10 项）。

### 14.6 还没做的

- **惰性保存**：不管任务用不用浮点，每次中断都保存 512 字节；真机上有 `CPACR` 的 trap 位可以做 lazy FP，省掉大部分开销
- **更宽的状态**：SVE 的 `z0–z31` 与 `p0–p15` 完全没碰（cortex-a72 也没有）
- **内核态 FP 隔离**：内核用 FP 不恢复原值（它自己不需要）

## 15. W^X（用户侧）

### 15.1 目标

用户代码页必须"能执行但写不进去"，栈页必须"能写但执行不了"。两者同时成立，注入一段自己改过的代码这条路就断了。

### 15.2 一个差点埋进去的编码错误

第一版把代码页设成 `AP=0b10`，注释写的"EL1 可读写、EL0 只读"。跑起来立刻出事：`iso` 程序在打印完前两段之后触发 `Data Abort(低 EL)`，`FAR` 指向 `.rodata` 里的字符串。

原因是 AArch64 的 AP[2:1] 不是"两段独立开关"：

| AP[2:1] | EL1 | EL0 |
|---|---|---|
| 0b00 | 读写 | **无访问权** |
| 0b01 | 读写 | 读写 |
| 0b10 | 只读 | **无访问权** |
| 0b11 | 只读 | 只读 |

`bit2=1` 是"只读"，`bit1=0` 是"EL0 不可访问"。所以 `0b10` 把 EL0 彻底关在门外——不只是不能写，连读和执行都进不去。正确值是 **`0b11`**：两级都只读，配合 `UXN=0` 就得到"可读、可执行、不可写"。

### 15.3 内核怎么还能写代码页

代码页物理地址来自页帧池（`0x4800_0000` 以上的 RAM），内核页表用 2 MiB 块把它映射成 `EL1 RW`。用户页表里同一物理页映射成 `0b11`。**同一个物理页，两套页表两种权限**——这正是"加载时内核能写、运行后用户改不了"的标准做法，不需要临时改页表属性。

前提是 `load_image` 必须在 `activate(space)` 之前调用（此时还在内核页表上）。现有调用顺序满足这一点。

### 15.4 证据

`user/wx.S`：先打印 `WX start...`，然后 `str` 到自己代码页的 `0x4440_0000`。

```
WX start...
  EC      = 0x24 (数据中止(低 EL))
  FAR     = 0x0000000044400xxx  (访问地址)
  → 任务 1 被终止
```

`make test` 断言 `FAR` 落在 `0x4440_0xxx` 区间。

顺带一个副作用：`iso` 测试原来把数据写在代码页 `+0x800` 处，W^X 一生效它自己就被拦了——数据已经挪到栈页 `0x4440_2200`。

### 15.5 还没做的

- **内核自己的 W^X**：内核代码用 2 MiB 块映射，粒度太粗（代码段与数据段/页表挤在一起），做不到代码页只读。要做得先把内核段拆到 4 KiB 粒度
- **栈的执行保护只靠 UXN**：栈页 `UXN=1` 已经不可执行，但 `PXN` 位没设（EL1 仍可从中取指，影响很小）
- **没有 `mprotect`**：页权限在创建时定死，运行期改不了

## 16. 系统调用表与主动让出

### 16.1 现有调用号

沿用 AArch64 Linux 的编号，省得以后移植用户程序时改。

| 号 | 名称 | 状态 |
|---|---|---|
| 64 | write(fd, buf, len) | ✅ 仅 fd=1，且只接受用户态指针 |
| 93 | exit(code) | ✅ 退出码写进 ASTER_USER_CTX[13] |
| 124 | sched_yield() | ✅ 主动让出 CPU |
| 172 | getpid() | ✅ 返回任务号（从 1 起） |

`svc_handler` 里 `match nr` 只有这四条，其余走 `ENOSYS` 返回 `-38`。

### 16.2 yield 的返回值约定

同步异常返回路径只有两种出口：

- 处理器返回 **0** → 汇编做 `LOAD_FRAME`，用栈上那份（可能已经被换过的）陷阱帧恢复现场
- 处理器返回 **非 0** → 判定"没有任务可跑"，`add sp, #800` 丢掉陷阱帧并回内核 shell

所以 `yield_current` 必须先把当前帧存回 `Task.ctx`，再 `pick_next` + `load_into` 把**下一个任务**的帧写进同一块栈空间，然后返回 0。如果只让出而不换人（只有一个任务），`pick_next` 会绕回自己，无害。

### 16.3 证据

`user/yield.S`：两个任务各打印 8 行 `Y<n>`，每行后调 `sched_yield`。

```
Y1
Y2
Y1
Y2
...
```

严格交替。如果 yield 不生效，会看到某一边连刷（时间片是 2 ms，打印一行远快于 2 ms）。这条断言已进 `make test`。

### 16.4 还没做的

- **阻塞态**：没有 `State::Blocked`，等 I/O 只能用自旋。这是 #14（每任务内核栈）之前必须先想清楚的地方
- **参数校验**：`write` 的指针检查只有范围判断，没检查页权限
- **没有 errno**：错误直接返回负数

## 17. 抗锯齿渲染

### 17.1 字模从二值改成 4-bit 灰度

原来字模是 1 bit 一像素，8×16 的 ASCII 每字 16 字节。缺点是笔画边缘全是硬台阶——16px 的汉字在 1024×768 上看着毛刺。

现在每个像素 4 bit（16 级），ASCII 每字 64 字节，汉字每字 128 字节，663 字合计约 90 KiB。生成时直接把 PIL 的灰度值量化到 0–15，绘制时 `alpha = nibble * 17`，按 alpha 混合：

```
dst = (src * a + dst * (255 - a)) / 255
```

`a == 255` 时走快速路径直接写，避免无谓的读-改-写。

### 17.2 圆角：覆盖率而不是"画个弧"

`rounded_rect_alpha(x, y, w, h, r, color, a)` 把矩形拆成五块：中间大块 + 左右两个窄条 + 四个角的 r×r 方块。四角逐像素算"到圆心的距离"，用 `d` 与 `r` 的差算出覆盖率，再乘 alpha 混合。这样圆角边缘能自然过渡，不需要预先画好的遮罩。

**`f32::sqrt` 在 `no_std` 里拿不到**（`sqrt` 是 std 提供的），第一版编译直接报 `no method named sqrt`。改成整数方案：距离用半像素为单位表示（`cx = 2*rr - 2*dx - 1`），自己写一个牛顿迭代的 `isqrt`，最后 `cov = 2*rr + 1 - isqrt(...)`，`cov >= 2` 就是满覆盖。

### 17.3 投影

`drop_shadow` 画三层同心圆角矩形，各向外扩 4/8/12 px，alpha 都是 16。叠三次之后边缘是 4 级左右的阶梯衰减，在深色壁纸上足够柔和。窗口本体随后覆盖上去，只有外圈露出来。

代价是填充率：一层阴影盖住约 50 万像素，三层 150 万，每个像素都要读-改-写。QEMU TCG 下这一屏大概多花 10 ms。目前桌面只在脏标记触发时重绘（60 ms 节流），还能接受；等做窗口拖拽就必须上脏矩形，只重画变化区域。

### 17.4 其它小件

- 壁纸渐变用 `i * i` 做非线性映射，上部暗得快、下部亮得慢，比线性渐变有层次
- 图标卡：顶部 1 px 内高光（`lighten(bg, 52)`）+ 底部 1 px 内暗边，只画中间直段避开圆角
- 标题栏与窗体同圆角半径，下边用矩形补齐成直边；标题栏顶部 1 px 高光线同样避开圆角段
- 三个窗口按钮从方块改成 12 px 直径的圆点（红黄绿），跟常见桌面对齐

### 17.5 还没做的

- **没有脏矩形**：整屏重绘，1024×768 一次 3 MiB 写入
- **没有离屏合成**：壁纸每次重绘都重画，浪费
- **没有 gamma 校正**：直接在 sRGB 上线性混合，深色背景上文字会略偏亮

## 18. 鼠标与光标图层

### 18.1 两个 virtio-input 变成一台"输入子系统"

virtio-mmio 的 32 个槽里，QEMU 默认把 `virtio-keyboard-device` 和 `virtio-mouse-device` 排在 30、31。两者 DeviceID 都是 18，光看 ID 分不出来，所以初始化时先写 `select = 1`（`VIRTIO_INPUT_CFG_ID_NAME`）再读 8 字节起的设备名字符串，命中 "Mous" 就当鼠标，否则按键盘处理。

事件格式两边一样：`u16 type / u16 code / u32 value`。键盘认 `EV_KEY`(1)，鼠标认 `EV_REL`(2) 累加坐标、`EV_KEY` 里的 `BTN_LEFT`(0x110) 记录按下和抬起。8 个描述符的缓冲池两家各一套，互不干扰。

### 18.2 光标不进桌面重绘

整屏重绘在 1024×768 上要写 3 MiB，鼠标移动显然不能走这条路。做法是把光标当独立图层：

1. 移走前，把 `SAVED` 里存的 16×16 背景写回原位
2. 在新位置读一遍背景存进 `SAVED`
3. 贴箭头（`FILL_MASK` 白色实体 + `EDGE_MASK` 外扩一圈的深色描边）

一次移动只碰 256 个像素。

箭头位图不是手搓的：用 PIL 在 8 倍超采样下画多边形，缩到 16×16，再对外形做一次 8 邻域膨胀、减去原形得到描边环。这样白色主体有 72 个像素、描边 46 个，压在任何底色上都能认出来。

### 18.3 帧号：解决"重绘把光标盖掉"

桌面重绘会连光标一起覆盖，但 `update()` 原先靠"坐标有没有变"判断要不要重画，位置没动就提前返回——结果光标被盖掉后再也回不来。现在 `draw_desktop()` 结束时给 `FRAME` 加一，光标记住自己上次贴图时的帧号，帧号变了就重贴，跟坐标无关。

顺带把 shell 里直接调 `render_dashboard()` 的那处改成走 `ui::redraw()`，重绘入口统一，不再有绕过节流的路径。

### 18.4 拖拽

`ui::tick()` 里先取点击队列：落在标题栏（窗口 y 到 y+38）内就进入拖拽态，记下按下点与窗口原点的偏移，之后每次移动都用这个偏移算新原点，夹在 `x ∈ [-560, 980]`、`y ∈ [34, 660]`，让窗口不至于整块飞出屏幕。松手退出拖拽态。

拖拽期间仍然是整屏重绘，60 ms 一次节流。这是 UI-7 要改的地方：只重绘"旧窗口矩形 ∪ 新窗口矩形"，光标只重贴一次。

### 18.5 这一轮没做到的

- 无头环境下 QMP 的 `input-send-event` 和 HMP 的 `sendkey` 都不会路由到 virtio-input 设备，VNC 的 PointerEvent 同样进不来。所以"鼠标真的动起来"只能在有显示后端的桌面上验，本地只验到了设备识别、缓冲提交和光标贴图。
- 点击队列 8 项，快速连点会丢事件，UI-7 一并换成 32 项环形队列。

## 19. 桌面合成与脏矩形

### 19.1 静态层缓存

桌面里真正会变的东西只有三样：窗口在哪、终端里写了什么、底栏时钟和指示灯。其余（壁纸渐变、两团柔光、顶栏、四个图标、底栏按钮底板）画一次就不再变。

`cache_wall()` 在开机时把这些画进一块 3 MiB 的缓冲（1024×768×4，放在内核 .bss 里，不占文件体积）。做法是把 `FB.base` 临时指到这块缓冲，所有绘图函数照常跑，画完再指回来。之后每次重绘开头只是一次 `restore_wall(0,0,1024,768)` 的内存拷贝，省掉十几万次渐变插值和字形混合。

缓存地址一开始想放 `0x4700_0000`，但 `-m 512M` 的机器物理内存只到 `0x2000_0000`，那块地址根本没有存储器件，写下去要么丢失要么 data abort。放 .bss 里最稳：内核映像 187 KB，加 3 MiB 仍在页帧池 `0x4800_0000` 之下。

### 19.2 拖拽只碰两块矩形

`move_window_to(nx, ny)` 干三件事：

1. 取旧原点与新原点的并集矩形（`848+|dx|` 乘 `602+|dy|`）
2. 从静态层缓存把这块拷回去，旧窗口连同阴影一起被抹平
3. 在新原点整块重画窗口，`term_guard` 会顺带把终端内容重画到新位置

指针移动过程中坐标每帧都变，所以并集通常是"窗口加一条细带"，比整屏 786 KB 像素少一半左右；拷贝比重新计算便宜一个量级。

### 19.3 还没拆干净的地方

- 窗口外的顶栏文字仍属于静态层，`ex3_short` 变了需要重新 `cache_wall()`，目前它启动后不变所以没处理
- 底栏时钟每帧重画，没有单独脏区
- 仍然只有一个窗口，`draw_window` 是硬编码的；多窗口要先把窗口抽成结构体，再按 z 序合成

## 20. 时钟与时区

QEMU virt 机器挂了一个 PL031（`0x0901_0000`）。`RTCDR` 是自 1970 起的秒数，`RTCCR` 的 bit0 是使能位。默认 `-rtc base=utc`，上电值就是宿主机当前 UTC，所以内核只做一件事：读出来加 8 小时。

读到的值小于 1.5e9（2017 年）就当没有时钟——说明这版机器没给 RTC 供电，底栏退回显示运行时长。

年月日换算走 Howard Hinnant 的 `civil_from_days`：先把秒数除成"自 1970 的天数"，再用 400 年一循环的 era 公式拆出年月日。纯整数运算，不查表也不占空间。

底栏 `00:18` 是这个结果，顶栏横幅也是。

## 21. Extreme 权限

安卓那套 root 的对应物。内核里就是一个 bool，`ex` 打开、`ex off` 关掉，提示符跟着在 `$` 和 `#` 之间切换。

打开之后才允许 `peek` / `poke` 直接读写物理内存的 8 字节。`poke` 额外要求 8 字节对齐、地址落在 `0x4000_0000-0x5000_0000` 之内，越界直接拒绝——不是怕人乱写，是怕写进没有存储器件的地方触发 data abort 把整机带走。

实测 `peek 0x40200000` 读到内核第一条指令 `0x9100003f580001c1`，`poke 0x46000000` 写进 `0x1122334455667788` 再读回来一模一样。

这是个本地控制台权限，没有密码也没有远程入口：能敲键盘的人本来就能重启机器。真要分出等级，得等 AF 系列把镜像信任根搬上磁盘之后，用引导器的签名结果当凭据。

## 22. 字体与文案

字模从 DroidSansFallback 换成文泉驿正黑。文泉驿自带 16px 点阵，小字号下比矢量字轮廓清楚，笔画实。

换了字体之后暴露一个问题：原来的渲染按字体度量算基线，`关` 之类字形会被顶出 16×16 格子，屏幕上显示成 `天`。改成先画到两倍画布、按实际笔画范围裁剪、再居中贴进格子，跟字体度量彻底脱钩。

文案也清了：启动时那个六行 ASCII art 的 ASTER 去掉了，换一行 `Aster 0.6   ARM64   2026-11-27 00:18 CST`；`原创内核 · 无任何第三方内核依赖` 这种自我宣告删了；提示符从 `aster>` 收成 `$` 或 `#`。

## 23. 磁盘：AsterDisk 与 virtio-blk

磁盘是阶段三的地基，先做格式和驱动，文件系统（AF-3）还没上。

`AsterDisk` 只用扇区头两层：扇区 0 是磁盘头（`ADSK` magic、版本、扇区大小、总扇区数、卷名 32 B、覆盖前 48 字节的 CRC32），扇区 1 是分区表（四项、每项 64 B：名字 16 B、起始 LBA、扇区数、类型、覆盖前 60 字节的 CRC32）。分区表空着的时候整盘没意义，`fmt` 就写一个 `asterfs` 分区，占 LBA 2 到盘尾。CRC 是我自己按 0xEDB88320 反射多项式算的，不依赖外部库。

驱动是新写的 `blk.rs`，仍然走 `virtio.rs` 里那套 modern MMIO 队列：reset → ACK → DRIVER → 关闭所有 feature → FEATURES_OK → 单队列 0 → DRIVER_OK。一个请求是一条三段描述符链：16 字节的请求头（类型、保留、扇区号）、512 字节数据段、1 字节状态；读的时候数据段打 `DESC_F_WRITE`，写完 `notify` 自旋等 used 环，超时上限五百万次。

有一处必须记下来：QEMU 6.2 的 virtio-mmio 默认 `force-legacy=1`，legacy 队列在这台机器上不消费描述符，`notify` 出去永远等不到 used，看起来像驱动死锁。`make run-disk` 和测试脚本都带了 `-global virtio-mmio.force-legacy=false`。

`disk` 命令读头部和分区表，校验两道 CRC，把卷名、版本、每个分区的 LBA 区间和类型打出来；`fmt` 要求 Extreme 权限，写完自动回读一遍。实测格式化后扇区 0 落盘是 `ADSK 01 00 00 00 00 02 00 00 00 40 00 00 aster...`，重启一个新进程再 `disk`，卷名和分区原样读回，CRC 一致。

## 24. AsterFS v0

文件系统落在 AsterDisk 的分区 0 上，块 4 KiB，块号相对分区起点算。布局是死的：块 0 超级块，块 1 inode 位图，块 2 块位图，块 3..7 是 inode 表（256 项，每项 64 B），块 7 往后是数据。8 MiB 的盘算出来 2047 块，去掉元数据剩 2040 个数据块。

超级块里放 `AFS1` magic、版本、块大小、总块数、inode 数、根 inode 号（固定 0）、inode 表和位图的位置、数据区起点、空闲块数，外加一个覆盖前 56 字节的 CRC32 和一个 32 字节卷名。CRC 算法和 AsterDisk 用的是同一份。

inode 只留 10 个直接块指针，没有间接块。一个文件最大 40 KiB，但 `wr` 现在按单块 4 KiB 写，多块读的能力已经在了，写要等 AF-4 的块缓存。

目录也是文件：目录的数据块里排着 32 字节一条的目录项——名字 24 字节、inode 号、类型。`list` 遍历目录块的条目时不能顺手去读 inode 表，因为那会覆盖同一个块缓冲，把还没走完的目录数据冲掉。所以另开一个第二缓冲区专给"查 size"用，`inode_size()` 走那条路。

格式化流程：写超级块 → 位图（inode 0 占用、块 0..7 占用）→ inode 表（0 号是根目录，size 64 字节，挂块 7）→ 块 7 写两条目录项 `.` 和 `..`。之后 `ls` 看到的是空目录，因为 `.` 和 `..` 在遍历时按 ino 非零过滤掉了。

命令行这一层加了 `mkfs / ls / cat / wr / df`。`mkfs` 要 Extreme 权限，`wr` 同名文件走覆盖路径，先把旧数据块的位图位清掉再重新分配。

还有一处顺手修的：串口读行的分支原来只接 `0x20..=0x7E`，所有 UTF-8 高位字节都被丢掉，中文文件名根本打不进去。放宽到 `0x80..=0xFF` 之后 `wr cn.txt 星芒系统 hello` 能正常写入读出，18 字节对得上。

## 25. 视觉体系：字体、色板、图标与间距

界面从"能显示"改成"看着不刺眼"，改的是四件事。

**字体分两层**。终端用 JetBrains Mono 13px 烘成 8×16 的 4-bit 点阵，每字符正好一格，等宽天然对齐；界面文字（顶栏、侧栏标签、标题栏、底栏）用 Inter 13px，格宽 10px，两套 ASCII 表分别落在 `font.rs` 和 `font_ui.rs`，汉字共用一张 16×16 的表。`draw_text_ui` 按 10px 推进、汉字按 16px，混排时中英各占其格。

**行高从 16 提到 20**。`term::ROWS` 跟着从 26 降到 22，一屏 22 行 440px。日志密不是字号问题，是行距问题——字没变大，只是每行之间留了 4px 的呼吸。

**色板换成中性灰**。以前是 `#0b1119` 打底、`#213a54` 渐变的海洋蓝，饱和度高、像屏保。现在背景 `#1d1f24 → #121316`，窗口 `#212328`，标题栏 `#2f343c` 比底色亮一阶，终端内容区反而更暗（`#141619`），靠三层明度差把层级拉开，只留一个强调色 `#5b99ff`。语义色也定死了：`OK #46c46a`、`WARN #d9a441`、`ERR #f2686a`、`DIM #6a7179`。

终端里的颜色按行判定，不逐字符调 API：行首 `$`/`#` 吃强调色，`!!!` 开头的行红，含 `FAIL` 红、`PASS`/`[OK]` 绿、`[EX]` 黄、`[IN]/[NET]/[BLK]` 灰。判定只读行首 12 个 ASCII 格，碰到汉字就停，成本是一次前缀扫描。

**图标换成线性图形**。原来侧栏是四个色块加字母（`>`、`S`、`N`、`i`），本质是占位符。现在在 `genfont.py` 里用 4 倍画布画线宽 2px 的矢量轮廓（终端折角、芯片四边引脚、WiFi 三段弧、圆圈 i），缩到 32×32 灰度存 `icons.rs`，运行时按 28px 最近邻贴上去。悬停时背后浮一块 `white @ 26/255` 的圆角底，选中时是 `accent @ 48/255` 的 pill 加左侧 3px 竖条——都是固定形状的 alpha 混合，不涉及动画。

**间距与阴影**。侧栏从 80 起、步距 88，标签离图标 9px；窗口 748×546，标题栏 44px、终端内边距 18px；阴影从三层小半径换成一层 26px 半径 18/255 + 一层 8px 半径 22/255，远的那层负责弥散，近的那层负责"落在桌面上"。底栏是一条 300×46 的半透明圆角 dock，`#0c0e12 @ 238` 打底再叠一层白 16/255 做玻璃反光，活动指示条是 26×3 的圆角短条。

还有一处跟性能有关的取舍：侧栏会随鼠标悬停变化，所以它不能留在静态壁纸层里，每次重绘在动态层画四个 28px 图标；窗口拖动时 `restore_wall` 擦掉旧区域后也要补画一遍侧栏，否则窗口压过再移开，侧栏就没了。

## 27. 多窗口（UI-7）

单窗口模型止步于"能拖"，再往下必须先把窗口变成复数。改动集中在 `fb.rs` 1136 行之后和整个 `ui.rs`：

`pub const NWIN: usize = 3`；`struct Win { x, y, w, h, open }`；`static mut WINS` 里终端 748×546、系统 350×304、网络 372×224，三者默认都开着，位置互相错开一段，开机就是叠着的三层。层序交给 `ZORD: [usize; 3]`，数组尾部是最上面那层；`FOCUS` 单独记录焦点窗口，只影响标题栏三色点的亮度（焦点 255、其余 96）。

命中测试分两步：`hit_top(x, y)` 从 `ZORD` 尾部往前找，第一个 `open` 且矩形包含点的就是目标；`title_hit(i)` 再判一次是否落在该窗口 44px 的标题栏里。点中标题栏就 `raise(i)`（把该窗挪到 `ZORD` 尾部）并开始拖拽，点中窗口主体只 `raise` 不拖，点空白处不改层序。

拖动做到窗口粒度：`move_window(i, nx, ny)` 用新旧位置的并集矩形 `restore_wall` 擦一次静态层，然后全量 `draw_all()`。三个窗口叠在一起时，并集擦除会连带擦掉压在上面的其他窗口，所以重画必须是整体重画，而不是只重画被拖的那一个——代价是拖动时每帧画三个窗口，但窗口内文字量（22 行终端 + 十行 kv）远小于 1024×768 全屏填充。

## 28. 树莓派路径：从"能编译"到"能启动"

这轮做的是让同一个内核真正跑在树莓派上，而不是只编出一个文件。

**三处非改不可的东西。** 第一是内核基址：树莓派固件把 `kernel8.img` 固定加载到 `0x80000`，内核原来链接在 `0x200000`，bss 一路铺到 `0x5C0000`。QEMU 的 raspi 模型会把 framebuffer 分配在 `0x300000` —— 正好压在内核 bss 里，第一次 `clear()` 就把内核踩穿了。把内核挪到 `0x800000`（8 MiB）之后两边不打架，真机上同样安全。第二是页表：原来 `[0, 1GiB)` 整段按 device 映射（QEMU 的 MMIO 全在那里），但树莓派的内核自己就在这段 RAM 里，device 内存带 XN 位，取指直接挂。现在树莓派分支把 `[0, 1GiB)` 拆成 512 个 2 MiB 块，`0x3F00_0000` 以上 16 MiB 标 device（外设窗口），其余标 normal。第三是页帧池：QEMU 用 `0x4800_0000`，树莓派没有这段，改成 `0x3000_0000`，从 `board.rs` 取。

**mailbox 驱动**（`kernel/src/mailbox.rs`）。property 通道 8，五个 tag 串起来发一次：`SET_PHYS_WH`、`SET_VIRT_WH`、`SET_DEPTH(32)`、`SET_VIRT_OFFSET(0,0)`、`ALLOCATE_BUFFER(对齐 4096)`，再补一个 `GET_PITCH`。写进 mailbox 的是**总线地址**（物理 + 偏移，BCM2837 是 `0x4000_0000`，BCM2711 是 `0xC000_0000`），拿回来的 framebuffer 地址同样要减偏移。这里有个坑：QEMU 的 raspi 模型直接给物理地址（实测 `0x300000`），减偏移会下溢成天文数字，所以判据写成"小于 RAM 大小就当物理地址用"。

**像素格式**。QEMU 的 ramfb 是 XRGB8888，树莓派的 framebuffer 是 BGRA8888。一开始我加了一层红蓝互换，后来实测读回值和写入值完全一致 —— 两者在小端内存里的字节顺序都是 B、G、R、X，本来就一样，换来换去反而把蓝色界面涂成橙色。这层已经撤掉，只留一条注释。

**现状**。raspi3b 上整条链路是通的：引导器三级 AVP 校验 PASS、EX3 生成、内核进 EL1、MMU 与 GICv2 起来、`board.rs` 认出 BCM2837、mailbox 拿到 `1024×768` 的 framebuffer、`clear()` 之后读回 `0x141619` 与写入一致、进入 shell。**QEMU 6.2 的 raspi3b 不会把这块内存同步到 `screendump`**，所以截图仍是白的 —— 这是 QEMU 的显示层限制，真机是 HDMI 直出，不经过 QEMU。

EMMC（SDHCI）和 USB HID（xHCI）还没接，`board.rs` 里已经占好位（`BlkKind::SdHost` / `InputKind::UsbHid`），下次从这里往下做。

## 29. VFS 与 fd 系统调用

用户程序原来只会 `write / exit / getpid`，读文件只能在 shell 里做。这一层补上"程序自己能打开文件读"。

**fd 表**（`kernel/src/vfs.rs`）。16 槽，0/1/2 留给标准流，3..15 给用户。每个 fd 记 inode、当前偏移、长度、读写位、文件名，外加一块 4 KiB 的页缓冲 —— open 时把文件内容读进这块缓冲，之后 read 只往前拷，不再碰磁盘；close 时若可写就整体写回并 `sync`。

**路径解析**。`/motd` 与 `motd` 等价，逐段走 `afs::dir_find`，`apps/demo/classes.dex` 这种多级路径也能走。段名上限 24 字节，与 AsterFS 的目录项一致。

**系统调用**。56 openat（dirfd 忽略，`O_WRONLY`/`O_CREAT` 映射成 vfs 的写位）、57 close、63 read、64 write（fd≥3 走 vfs，1/2 仍走串口）。用户指针逐个过 `mmu::user_ptr_ok`，字符串逐字节读，不跨页越界。

EL0 跑 `file` 程序（openat → read → 打印 → close）的串口实录：

```
[VFS] fd 表 16 槽就绪（0/1/2 留给标准流），切 EL0 执行 openat → read → close
[SVC] openat("/motd") → fd 3
[SVC] read(fd=3, 96) → 30 字节
Aster VFS openat read close OK
[SVC] close(3) → 已释放
[VFS] 任务结束，退出码 0
```

写路径另用 `vfw` 验：新建 → 写 44 字节 → close 落盘 → `read_file` 读回一致，`fd` 显示 `open 1 / read 0 / write 1`。

**没做的**：fd 表还是全局一份，不是每任务一份；`lseek` / `fstat` / `readdir` 没有；单文件上限仍 4096 字节（AsterFS v0 只有 10 个直接块，等间接块做完再放宽）。

## 30. APK 容器：先能取出来

要跑 APK，第一块不是 DEX 解释器，是从 zip 里把 `classes.dex` 原样取出来。

EOCD 在文件尾部，注释最长 65535 字节，所以倒扫最后 64 KiB + 22。找到后从中央目录偏移开始逐条目读：名字、压缩方式、压缩/原始大小、本地头偏移。**数据真正开始的偏移必须按本地头重算** —— 本地头的名字/扩展字段长度和中央目录可能不同，直接用中央目录的长度会读到别人家的数据。

## 32. 开机动画：一束光长成星芒

设计约束：不能像 HarmonyOS 那套（多层圆环扩散 + 手写体字标 + 底部标语）。所以整支动画只做一件事 —— **六个尖依次从黑场里长出来，再散开**。没有粒子雨、没有网格、没有圆环叠加。

**时间轴**（2400 ms）：

| 区间 | 画什么 |
|---|---|
| 0–200 | 黑场里一个点亮起 |
| 200–1100 | 六个尖依次生长（每个错开 90 ms，ease-out），整体缓慢自转（4.4°/100 ms）|
| 1100–1600 | 完整星芒自转 |
| 1600–2100 | `Aster` 与 `星芒 · 原创内核 · ARM64` 淡入 |
| 2100–2400 | 星芒放大散开、亮度衰减，整屏过渡到 `0x1a1d22` |

**实现上的几个决定**：

- `no_std` 没有三角函数，自带一张 `sin(0..90°) ×1000` 的表，四象限查表得到 sin/cos。
- 每个尖是三个三角扇形的并集（根部略宽、尖端极细），扫描线填充，边缘用 `blend_px` 做一像素过渡。
- 每帧只重画中心 600×600 的方块，背景按竖向渐变精确重建。全屏重绘在 QEMU 上要写 786k 像素/帧，会明显掉帧。
- 光晕只用贴身的小半径两层。试过 7 层大同心圆，暗背景上每一层的 alpha 台阶都看得见，像靶心，反而掉质感 —— 去掉。
- 收尾过渡到 `0x1a1d22`，和桌面壁纸顶部 `0x1d1f24` 几乎同色，切桌面时没有跳变。

**顺带修掉一个真 bug**。`fb::circle` 里把参数 `cx/cy` 遮成了像素坐标，写屏时用的是 `3*dx-3*r+1`，所有圆整体错位，半径越大偏得越远。修好之后桌面的三色点、状态灯、dock 圆点才落在该在的位置。

**取证**：`bootframe <ms>` 把动画任意时刻静态画出来并停在屏幕上。内部置一个 `HOLD` 标志让 `ui::tick` 停止重绘 —— 否则下一拍 `render_dashboard` 就把这一帧盖掉了。QEMU 的 ramfb 在 `-display none` 下运行中抓 `screendump` 会拿到撕裂帧，所以静态帧是唯一可靠的取证手段；真机 HDMI 输出不受影响。

### 32.1 第二版打磨

第一版能看，但细看有三处不足：瓣像"刀片"（三块三角硬拼，边缘见台阶）、收尾是整体放大（像球在膨胀，不像星芒散开）、字标是原地淡入（缺方向感）。第二版逐条换掉：

| 项 | 第二版做法 |
|----|-----------|
| 瓣形 | 单瓣用三个共轴四边形叠画：宽光晕层（0x4f7ec0，α52）+ 主色层（ACCENT，α150）+ 细亮芯（0xdaeaff，α80）。层宽不同，边缘互相错开，天然柔和，不再有单层三角的硬台阶 |
| 生长感 | 每瓣生长期间在尖端跟一个"笔尖"光点（r5 淡蓝 + r2 纯白），长到 95% 时收掉 —— 视线知道光往哪走 |

版本号同步升到 **0.8**（顶栏、系统面板、串口启动行三处）。顺带修了顶栏 EX3 指纹：原来传 `EX3_TAG[..13]` 再拼一个 "EX3 " 前缀，重复且溢出屏幕右边被裁，改成取末 8 位（如 `9337BDCD`）。

## 33. DEFLATE 解压（APK-2）

APK 里真实应用的条目基本都是 method 8，`classes.dex` 尤其如此 —— 只支持 stored 的容器层等于只能读自制包。这一节是 inflate 的实现和取舍。

`kernel/src/inflate.rs`，约 330 行，三条路径：

| 块类型 | 处理 |
|--------|------|
| 00 stored | 对齐到字节边界，读 LEN/NLEN 并校验互补，逐字节搬 |
| 01 固定 Huffman | 按 RFC 的字面/长度码长（8/9/7/8）建表，距离码 32 个 5 位码 |
| 10 动态 Huffman | 读 HLIT/HDIST/HCLEN + 码长码（19 个符号按固定顺序），再解码长序列（含 16/17/18 重复码），最后建两张表解数据 |

解码不用查表法，而是 canonical 码的经典两步：`count[len]` 数出每层码数，`symbol[]` 按序排好，解码时逐位推进 `code/first/index`。比一次建满 15 层查找表省三分之二代码，对几百 KB 的 dex 速度足够。

LZ77 回拷就是逐字节 `dst[out] = dst[out - dist]`，天然处理 dist < len 的重叠（重复填充那种情况）。

**边界**（都是明确返回错误，不 panic）：位流提前结束、码长 > 15、Huffman 过订阅、符号索引越界、长度码 > 285、距离码 > 29、距离超过已输出数据、输出超出目标缓冲、块类型 3。

**输出缓冲**是 `shell.rs` 里一块 128 KiB 静态数组 `INFL_BUF`（BSS，不占镜像体积）。超过就报"输出超出缓冲"，不截断。

**取证**：`assets/demo2.apk`（595 字节，宿主侧用 Python zipfile 打）里三条目 —— `classes.dex` 6036 字节 deflate 到 153、`AndroidManifest.xml` 72 字节 stored、`assets/note.txt` 460 字节 deflate 到 30。内核 `apk2 dex` 解出的长度与 FNV-1a 64 指纹（`0x83a2ce9726977698`）与打包前完全一致，`apk2` 列表显示三条都还原到原始大小。这条已加进 `make test` 作为第 13 项断言。

## 34. 一次性逻辑复查（v0.8 收口）

用户要求"检查所有逻辑"，做了一遍静态扫查：

- **panic 面**：全模块只有两处 `expect` —— `SYS` 与 `FB` 的初始化护栏，未初始化就是编程错误，留着是对的；没有散落的 `unwrap`。
- **除零**：bootanim 的渐变用 `h.max(1)`，其余除法分母都是常量。
- **zip 容器**：EOCD 倒扫限最后 64 KiB + 22 字节；中央目录每项检查 46 字节头与名字长度；条目数据偏移按**本地头**重算（中央目录的 extra 长度不可信）；解包前检查 `data_off + csize <= len`。
- **vfs**：fd 索引先判范围再取；`read` 用 `len.saturating_sub(off)`；`write` 检查 `off + n <= 4096`；`close` 只在 `wr` 时落盘。
- **inflate**：见上一节。

复查中改掉一个真问题：`zip::extract` 的 stored 分支原来用 `min(out.len())` 静默截断 —— `apk cat` 拿 512 字节缓冲去读 6 KB 的 dex 会"成功返回"半个文件。现在改成超过缓冲直接报错。`apk2` 列表里解压失败原来显示 `→ 0`，改成打错误信息或"与原始大小不符"，免得把失败伪装成正常。

一处已知但暂不修的：VFS 句柄表仍是全局一份，不是每任务一份。现在只有一个 shell 持有句柄，等进程模型落地再改成 per-task。

## 35. DEX 解析与最小解释器（APK-3）

能解压出 `classes.dex` 只是把文件搬出来了。这一节是第一次真正"跑" APK：内核读 DEX 结构，执行一个方法，让 APK 里的字符串出现在 Aster 的终端里。

**结构遍历**（`kernel/src/dex.rs`）：header（魔数 / 版本 / file_size / endian_tag / adler32 checksum）→ `string_ids`（每项指向 string_data，uleb128 长度 + 0x00 结尾）→ `type_ids`（描述符索引）→ `proto_ids`（shorty / 返回类型 / 参数表）→ `method_ids`（class_idx / proto_idx / name_idx）→ `class_defs`（找 class_data_off）→ class_data（static/instance fields 跳过，direct methods 的 method_idx_diff 累加）→ code_item（registers_size / insns）。

**解释器**只认六个 opcode，但足够跑通一条完整链路：

| opcode | 语义 |
|--------|------|
| 0x00 nop | 跳过 |
| 0x12 const/4 | 4 位字面量入寄存器（含符号扩展） |
| 0x13 const/16 | 16 位字面量 |
| 0x1a const-string | 寄存器里存字符串索引，用时才解引用 |
| 0x71 invoke-static | 35c 格式，按 C/D/E/F/G 取参数寄存器；只桥接 `Lcom/aster/Log;->i(String)` 到内核 `println` |
| 0x0e return-void | 结束，返回已执行指令数 |

不认识的方法和 opcode 都打印出来并返回错误，不会"假装执行成功"。

**DEX 是自己拼的，不是 dx/d8 产物**（`tools/mkdex.py`）：按格式规范逐段写 header / map_list / ids / class_defs / data（string_data、type_list、class_data、code_item），最后回填 sha1 与 adler32。536 字节，任何校验器都能过。写进 `classes.dex` 的字节码就是三条：

```
const-string v0, "Hello from Aster, this string lives in a real DEX"
invoke-static {v0}, Lcom/aster/Log;->i(Ljava/lang/String;)V
return-void
```

**取证**：`dex` 打印结构（8 字符串 / 4 类型 / 2 原型 / 2 方法 / 1 类，checksum PASS）；`dex run` 打印那段字符串并报"2 条指令，正常 return-void"。已加进 `make test` 作为第 7 项断言。

到这一步，`APK → deflate 解压 → DEX 结构 → 字节码执行 → 内核输出` 整条链路是通的。剩下的解释器工作（算术、分支、字段、对象、`new-instance`、异常）是在这套骨架上加 opcode，不是重做。

### 35.1 第二版：循环、分支、算术

第一版只证明"字节码能进来"。第二版的 `run()` 是一段真程序：

```java
static void run() {
    int sum = 0;
    for (int i = 1; i <= 5; i++) sum += i;   // 15
    Log.n(sum);
    Log.i("loop done");
}
```

对应 19 个 code unit，opcode 扩到 15 个：`move`、`const/4`、`const/16`、`const-string`、`goto`、`goto/16`、`if-eq/ne/lt/ge/gt/le`、`if-eqz/nez/ltz/gez/gtz/lez`、`add/sub/mul/div/rem-int`、`add-int/lit8`、`add-int/lit16`、`invoke-static`、`return`/`return-void`。

执行结果：`[DEX] 15` → `[DEX] loop done`，27 条指令后正常 `return-void`（5 轮循环 × 4 条 + 初始化 3 条 + 收尾 4 条）。

同时补上 `Lcom/aster/Log;->n(I)V` 桥接，能打印整数 —— 不然算术算了也看不见。

**写这个 fixture 时踩的两个编码坑，值得记下来**（都是"看起来对、跑起来错"）：

1. `if-gt` 是 22t 格式，寄存器编号在 unit0 的高 8 位：`B|A|op`。我先写成 `0x0135`（A=1, B=0），实际比较的是 `v1` 和 `v0`（sum=0），于是第一轮就 `1 > 0` 跳出去，和变成 0。正确编码是 `0x2135`（A=1, B=2）。
2. 分支目标算错：加了两条指令后 `if-gt` 的目标从 pc 10 变成还在 pc 10，但我照着旧注释写成 `+10`（跳到 pc 13 的 `const-string`），于是循环体被整段跳过。相对偏移必须跟着指令重排重新算。

两条都不是解释器的错 —— 解释器按 DEX 规范执行得很老实，错在 fixture 的编码。这也说明"解释器对了"不等于"程序对了"，fixture 的字节码得用反汇编核对（`mkdex.py` 跑完会把 insns 打出来）。

## 36. 对象、字段与虚方法（APK-5）

上一版解释器只能跑静态方法。这一版加了三样东西：对象堆、字段、调用栈。

**对象堆**：`static mut HEAP: [ObjState; 8]`，每个对象 8 个整型字段。`new-instance` 分配，寄存器里存的是堆索引（不是指针），因为内核还没有每进程堆；对象引用就是一个整数。

**字段**：`iget/iput`（22c）直接用 field_idx 当槽号 —— v0 的 field_ids 只有一项，够 demo。真实现要按类布局算偏移，这一步先跳过。

**调用栈**：`exec()` 递归，深度上限 8。`invoke-direct` / `invoke-virtual` / `invoke-static` 走同一条路径：取参数寄存器 → 递归执行 → 返回值写进调用者的 `last`，`move-result` 再搬进目标寄存器。

**fixture**（`tools/mkdex.py` 第三版，918 字节 dex）：

```java
class Counter { int v; Counter(int x){v=x;} int next(){v=v+1;return v;} }
static void run() {
    Counter c = new Counter(10);
    Log.n(c.next());   // 11
    Log.n(c.next());   // 12
    Log.i("objects ok");
}
```

**结果**：`[DEX] 11` / `[DEX] 12` / `[DEX] objects ok`，22 条指令后退回。

### 写 fixture 时又踩的三个坑

这一版在 fixture 上连踩三次，都记下来，因为它们是 DEX 里最容易反复错的地方：

1. `ins_size` 忘了算 `this`。实例方法 `<init>(I)V` 的 ins_size 是 2（this + int），我写 1，解释器在参数个数检查上直接拒绝。
2. `virtual_methods` 的 `method_idx_diff` 从 0 重新累加，不是接着 direct methods 的最后一个。我按"接着"写，导致找 `next` 时索引指向别处。
3. `22c` 格式里 B（对象寄存器）在 **unit0 的高 4 位**，unit1 整 16 位都是字段索引。我把 B 写进 unit1 高 8 位，字段索引变成 0x0100，越界。
4. 附带：`const/4` 只装得下 -8..7，给构造器传 10 必须用 `const/16`（占 2 个 code unit，后面所有 pc 跟着挪）。

第 3 条和第 4 条都是"编码错了但格式校验不报错"，只有真的执行才会露出来。所以 fixture 每次生成都会打印反汇编，人工对照语义 —— 这一步省不得。

## 37. USB：DWC2 主机模式与 HID 键鼠

树莓派没有 PCI 也没有 virtio，键鼠只能挂在 SoC 自带的 USB OTG 控制器上。BCM2837 用的是 Synopsys DWC2（`dwc_otg`），BCM2711 是同一颗 IP 的另一个地址。`kernel/src/usb.rs` 自己把这条链路走完，不借用任何现有内核的 USB 栈。

### 37.1 从设备模式切到主机模式

上电时 DWC2 默认是设备（peripheral）身份。要当主机用，顺序不能乱：

1. **核心软复位**：`GRSTCTL` 置 `CSftRst`，等它自己清零（最多 50ms）。这一步把所有 FIFO、通道、端点状态清干净，不做的话后面写 `HCCHAR` 全是未定义行为。
2. **强制主机模式**：`GUSBCFG` 清 `FDEV`（bit30）、置 `FHMOD`（bit29），`TRDT`（bits10..13）写 9 —— PHY 收发器转向时间，48MHz 下这个值才够。
3. **PHY 时钟**：BCM2837 给 OTG 的就是固定 48MHz，`HCFG` 选 0 即可。这一位选错会表现为"端口有连接但永远复位不完"。
4. **端口供电**：`HPRT0` 置 `PrtPwr`。规范要求 20ms 稳定时间，之后才能判连接。
5. **判连接**：轮询 `HPRT0.PrtConnSts`，最多 300ms。没插设备就到这儿停住，返回 `Idle`。

### 37.2 判断"这个地址上到底有没有控制器"

QEMU 的 raspi 机器没有给 USB 建模型，`0x3F98_0000` 读回来是别的外设的别名值。如果只靠"复位位能清掉"来判存在性，会误报成"初始化成功、端口空闲"—— 用户看到的是一个根本不存在的控制器状态。

判据用两个寄存器：`GSNPSID`（0x40，控制器版本号，真芯片永远不为 0）和 `GRSTCTL`（真芯片的 AHB Idle 位恒为 1）。两者都读回 0 才认定"这里没东西"，直接返回 `NoResponse` 并把地址打出来。这比猜更诚实：`usb` 命令会明说"QEMU 没建模型，真机上这个地址是真的"。

### 37.3 控制传输：手写 SETUP / IN / 状态三阶段

DWC2 不做 DMA 也能跑，全走 FIFO 模式，省掉地址映射和一致性问题。一次 `control()` 的流程：

| 阶段 | 动作 |
| --- | --- |
| SETUP | `HCTSIZ` = XFERSIZ 8 / PKTCNT 1 / PID=SETUP；`HCCHAR` = 控制端点 0 + ChEna + ChMPS；8 字节 setup 分两个 32 位手写进 `DFIFO0` |
| IN | 清通道 → `HCTSIZ` = 长度 / PKTCNT 1 / PID=DATA1 → `HCCHAR` 置 `ChDir` → 等 `HCINT.ChXferCompl` → 按字从 `DFIFO0` 读回 |
| 状态 | 零长 OUT，PID=DATA1，只等握手；失败不影响数据已经拿到 |

三个易错点：`PKTCNT` 在 bit19（不是 bit29），`PID` 在 bit29；`HCTSIZ` 的 PID 字段是"下一次要发的令牌"，不是刚发过的；`HCINT` 全部是写 1 清零，读改写会把别人的中断一起清掉。

### 37.4 枚举

拿到的设备直接走标准流程，地址固定分配 1：

- `GET_DESCRIPTOR(device, 18)` → VID / PID / `bDeviceClass`
- `SET_ADDRESS(1)` + 3ms 恢复等待
- `GET_DESCRIPTOR(config, 9)` 读 `wTotalLength`，再按这个长度读全量
- 逐条走描述符链：接口描述符里 `bInterfaceClass == 0x03` 的就是 HID，紧跟其后的端点描述符里 `bmAttributes & 3 == 3`（中断）且方向 IN 的，就是报告端点
- `SET_CONFIGURATION(1)`
- 类请求：`SET_PROTOCOL(boot, 1)` + `SET_IDLE(0)`，失败不致命（有些设备不实现）

### 37.5 HID boot 报告

只做 boot 协议，不做 report descriptor 解释 —— 这是覆盖率和代码量的最优解，市面上键鼠 99% 支持 boot 模式。

- 键盘 8 字节：`[modifier, 保留, key0..key5]`。按下/抬起靠"这一帧和上一帧的差集"算：上一帧有、这一帧没有 = 抬起；反之 = 按下。modifier 单独比对四个位（LCtrl/LShift/LAlt/LGui）。
- 鼠标 4 字节：`[按键位, dx, dy, wheel]`，位移是 `i8` 相对量。

键码要转成 Linux input event code（`input.rs` 的事件格式从 virtio 那会儿就定了，不因为换了通道而改）。`HID2LINUX` 是一张 67 项的查表：a..z、1..0、Enter/Esc/Backspace/Tab/Space、标点、F1..F11、小键盘。表外一律丢弃。

注入走 `input::inject_key(code, down)` / `inject_move_rel(dx, dy)` / `inject_btn_any(idx, down)`。位移用相对量是因为真实鼠标只报相对量；`sim` 的 `inject_move_to` 是绝对坐标，两者共存，走的都是同一个 `mouse_event()` 状态机，所以置顶、拖拽、开窗逻辑完全一致。

### 37.6 验证边界（必须说清楚）

QEMU 的 raspi3b 没有 DWC2 模型，所以**这一层在本地只能验到"不崩、状态诚实"**：

- QEMU virt：`usb` 打印"这块板子没有 DWC2 控制器"（`board.usb == None`）
- QEMU raspi3b：走完复位流程，`HPRT0` 没有 `PrtConnSts`，状态落到 `Idle`，`usb` 显示"端口 空闲 未使能"，`usb poll` 返回 0 事件
- 真机（RPi3B/4B + 键鼠）：`Ready` + VID/PID + HID 端点，尚未验证

未接的缺口：报告轮询还没挂到定时器/中断（现在要手动 `usb poll`）；只支持 boot 协议；滚轮没接；热插拔（拔出后 `PrtConnSts` 掉）没有重新枚举；低速/全速以外的速度没处理。

## 39. XCE：Aster 原生程序格式

APK / DEX 那条线解决的是"别人的程序怎么在 Aster 上跑"。XCE 解决的是另一件事：**Aster 自己的程序长什么样**。

它不是 ELF 也不是 PE，是一段"链接到 `0x4440_0000` 的 EL0 扁平二进制"外面套 28 字节头。这个地址是内核用户地址空间的代码页，从阶段二起就没变过。

### 39.1 头格式

| 偏移 | 大小 | 字段 | 说明 |
| --- | --- | --- | --- |
| 0x00 | 4 | magic | `"XCE1"` |
| 0x04 | 2 | version | 1 |
| 0x06 | 2 | kind | 0 = EL0 可执行，1 = 数据包，2 = 内核模块（未开放） |
| 0x08 | 4 | entry_va | 必须等于 `0x4440_0000` |
| 0x0C | 4 | body_size | body 字节数，上限一页 4 KiB |
| 0x10 | 4 | crc32 | body 的 IEEE CRC32 |
| 0x14 | 4 | stack_va | 期望栈顶 |
| 0x18 | 4 | flags | 保留 |
| 0x1C | — | body | 代码与只读数据 |

为什么不做段表：当前用户地址空间是固定的"一页代码 + 一页栈"，多段加载只会把 MMU 和页帧分配器拖进来。等到要支持堆和动态库再开 `kind=2`。

### 39.2 装载流程

`xce run` 做的事和 `run` 命令完全同源：

1. `parse()` 校验：魔数、版本、body 不越界、`body_size ≤ 4096`、CRC32、`entry == 用户代码页`
2. `sched::reset()` → `mmu::new_space()` → `mmu::load_image(sp, body)`（拷页 + `dc cvau` + `ic ivau` 刷 I-cache）
3. `sched::spawn(sp)` → `timer::arm()` → `mmu::activate(&sp)` → `enter_user_state(CODE, STACK_TOP)`
4. 程序里 `svc #0` 走 64=write、93=exit；任务全死时 `exit_current()` 发现 `pick_next()` 返回 `None`，切回内核页表，`enter_user_state` 返回退出码

实拍（`xce1.png`）：装载 71 字节 → 打印 `XCE ok: native program, EL0, Aster` → `[SVC] exit(7)` → 回 shell。

### 39.3 打包

`tools/mkxce.py` 用纯 Python 的 `struct + zlib` 打包，不依赖交叉工具链：

```
python3 tools/mkxce.py build/user/xce.bin assets/xce/demo.xce
```

`make image` 会先编 `user/xce.S`、objcopy 成扁平二进制、再打包成 `assets/xce/demo.xce`，内核用 `include_bytes!` 内嵌。所以 `xce run` 在没挂磁盘的情况下也能跑。

## 40. Device Lock（DL）

Extreme 与 DL 是两道锁，管的不是同一件事：

- **Extreme**：放开权限层级（提示符变 `#`，允许碰底层命令）
- **DL**：这台设备现在准不准动底层（内存写、磁盘格式化、固件刷写）

所以 `ex` 打开之后 `poke` 仍然被拒，必须再 `dl unlock`。这样"我进了 root 模式"和"我知道我在改哪台机器"是两次独立的确认。

### 40.1 解锁码

`EX3` 指纹的末 8 位。顶栏一直显示着 `9337BDCD`，引导器底层模式里 `dl` 也会打印。

这不是安全边界 —— 能看到串口的人本来就读得到 EX3。它的作用是**防误操作**：刷固件、格式化磁盘这类不可逆动作，要求手抄一遍本机构建标识。文档里要把这句话写清楚，不能假装它是鉴权。

### 40.2 覆盖范围

| 位置 | 命令 | 锁定时的行为 |
| --- | --- | --- |
| 引导器 | `flash` | 拒绝，并打印解锁码 |
| 内核 | `peek` / `poke` | 拒绝 |
| 内核 | `fmt` / `mkfs` | 拒绝 |

关于用 `peek` 只读也拦了这一条：读内核地址本身不改状态，但它和 `poke` 是同一套地址解析，拦一半留一半反而容易误操作。要么都放开，要么都锁。

锁状态不跨重启：每次上电默认锁定。持久化需要一块可信存储，那是后面的事。

## 41. 系统更新：A/B 槽与 AUP

### 41.1 更新包

`AUP1` 头 28 字节 + body：

| 偏移 | 字段 |
| --- | --- |
| 0x00 | magic `"AUP1"` |
| 0x04 | version u16（`0x0009` = 0.9） |
| 0x06 | build u16（0 = 任意构建） |
| 0x08 | body_size u32 |
| 0x0C | crc32(body) u32 |
| 0x10 | ex3[12] —— 本机 EX3 的前 12 字节 |
| 0x1C | body |

`ex3[12]` 是"这个包是给这台设备打的"的凭据。校验不过就拒绝，连 stage 都不给登记。

### 41.2 四步状态机

- `update check`：只读校验（魔数、长度、CRC、EX3 绑定、版本比较），不动任何状态
- `update stage`：校验通过后写 `upd.state`（`staged ver=0.9 pending`）
- `update apply`：写 `boot.conf` 的 `slot=B`，`upd.state` 记 `applied`
- `update rollback`：写回 `slot=A`，`upd.state` 记 `rolled-back reason=manual`

实拍（`upd5.png` / `upd6.png`）：`fmt → mkfs → stage → apply` 后状态变 `B（暂存更新）`；`rollback` 后回 `A`，`上次状态` 那行显示 `rolled-back slot=A reason=manual`。

### 41.3 现在还没真的生效

引导器仍然加载内嵌镜像。"从 B 槽读盘启动"需要引导器自己有块设备驱动 —— 那是 **BOARD-6**。在这之前 `apply` 会把这句话如实打出来，不假装重启就换版本了。

另外 AsterFS v0 单文件上限 4096 字节，装不下 370 KB 的内核镜像。BOARD-6 要一起解决：内核镜像走 disk 上的裸槽（不占文件系统），boot.conf 只记槽号。

## 42. SD 卡镜像

`make sdcard` 产出一个可以直接 `dd` 的 64 MiB 镜像：

```
sector 0        MBR：一个分区，type 0x0C（FAT LBA），从 sector 2048 开始
sector 2048 起  FAT16「ASTERBOOT」分区
                  config.txt    arm_64bit=1 / kernel8.img / enable_uart=1 / dtoverlay=disable-bt
                  kernel8.img   Aster 引导器（内含内核与校验链）
```

做法：先建独立的 FAT 分区镜像（`mkfs.vfat -F 16` + `mcopy`），再整块 dd 回主镜像的 2048 扇区处。全程不需要 root、不需要 loop 设备。

为什么 FAT16 而不是 FAT32：64 MiB 上 FAT32 的 cluster 数低于规范建议，mtools 直接读不了（`Error reading FAT`）。树莓派固件 FAT16/FAT32 都认，小镜像用 16 更稳。

为什么 MP4 里不做 ISO：ARM64 没有 PC 的 El Torito/CD 引导路径，对树莓派它就是一个 FAT 分区。硬做 `.iso` 只是换个后缀，不解决任何问题。要 ISO 的话，等 UEFI 那条线（QEMU `virt` 目前走 `-kernel`）。

## 43. APK-6：DEX 数组

前五个 APK 步骤之后，解释器缺的下一块是数组。Java 的 `int[]` 在 DEX 里是三条指令的组合：`new-array` 开、`array-length` 量、`aget`/`aput` 读写，数组对象本身在寄存器里只存一个引用号。

### 43.1 内核侧：数组堆

`kernel/src/dex.rs` 新增一块静态数组堆，和对象堆并列：

```rust
#[derive(Clone, Copy)]
struct Arr { len: u32, d: [i32; 8] }
static mut ARRS: [Arr; 4] = ...;
const ARR_TAG: u32 = 0x100;
```

寄存器里放 `0x100 + 槽号`，和对象堆的 `0x000 + 索引` 靠区间分开，不会撞。为什么不复用对象堆：对象堆的 `ObjState` 是 8 个"字段"（语义上是成员变量），数组是 `len` + 连续元素，两者的边界检查和越界行为都不一样，混在一起会让 `iget` 越界和 `aget` 越界共用一套错误判断，反而更难查错。

四个新 opcode：

| opcode | 名称 | 格式 | 语义 |
|---|---|---|---|
| `0x21` | `array-length` | 12x | `vA = len(vB)`，非数组报错 |
| `0x23` | `new-array` | 22c | `vA = new [I(vB)`，长度上限 8，type 必须以 `[` 开头 |
| `0x44` | `aget` | 23x | `vA = vB[vC]`，越界报错而不是读脏数据 |
| `0x4b` | `aput` | 23x | `vB[vC] = vA`，越界报错 |

23x 的寄存器全在 unit1：`C = unit1 >> 8`，`B = unit1 & 0xff`，A 在 unit0 的 bits 8-15。越界一律返回 `Err("数组越界")`，不静默截断——这和 `zip::extract` 那次修的毛病是同一条原则。

### 43.2 fixture（第四版，`tools/mkdex.py`）

```java
int[] a = new int[5];
int sum = 0;
for (int i = 0; i < 5; i++) { a[i] = i * 3; sum += a[i]; }
Log.i("array ok"); Log.n(sum);
```

期望 30（0+3+6+9+12）。29 个 code unit，dex 950 字节，`demo3.apk` 855 字节。实拍 `[DEX] 30`，51 条指令。

### 43.3 这次踩的四个编码坑（都是"格式对了但字节序写反"）

1. **`const/4` 的 lit 在高 4 位，A 在 bits 8-11。** 想写 `v5, #3` 写成 `0x5312`，实际被解成 `v3, #5`——寄存器 `v3` 恰好是求和累加器，于是第一版直接打印 `5`。正确：`0x3512`。
2. **`22b`（`add-int/lit8`）的 unit1 是 `B` 在高字节、`lit` 在低字节。** 写成 `0x0102` 被解成 `B=v1, lit=2`，`i` 一步从 0 跳到 258（`v1` 是数组引用 `0x100`），循环立刻出错。
3. **`0x93` 是 `div-int` 不是 `add-int`。** 想把 `add-int` 写成 `0x0393`，跑出来报"整数除零"——那一刻才意识到自己把 add 的 opcode 记成了 0x93。`add-int` 是 `0x90`。
4. **`30t` 分支偏移相对当前指令的 pc，不是下一条。** 出口在 pc 20、分支在 pc 7，偏移就是 13 而不是 12。这条 APK-4 已经记过，这次又"顺手"算错了一次方向：写成 `if-lt` 想表达"继续循环"，实际 `if-lt v2, v4` 成立就跳出口，第一次进来 `0 < 5` 恒真，直接退出得 0。改成 `if-ge`（`0x34`）。

四条合起来的教训很朴素：手搓 DEX 时，先让 `mkdex.py` 把自己生成的 code unit 反汇编打印一遍，人工对一遍再上机。现在脚本末尾就是这么做的，出问题先看那三行反汇编。

### 43.4 断言与回归

`make test` 的 DEX 断言从 `[DEX] 11` 换成 `[DEX] 30`，名称改为"数组：new-array + aput/aget + 循环求和 30"，总数仍是 18 项全 PASS。旧的 11 是 APK-5 对象 fixture 的产物，两个 fixture 都在仓库里（`demo3.apk` 是当前 `dex run` 用的默认包），断言跟着默认包走。

APK 主线下一站是 `StringBuilder` 与静态字段；数组本身够用了，但 `new-array` 现在固定上限 8 个元素、4 个槽——真要跑有意义的 APK，得改成按需分配，那要等页帧分配器给用户态开口子。

## 44. APK-7：静态字段与 StringBuilder

真实 APK 里 `StringBuilder` 出现的频率仅次于 `Log`。它和数组的区别在于：数组是 DEX 指令能直接操作的对象，`StringBuilder` 不是——它属于 `java.lang`，APK 包里**没有**这个类，它是框架（framework.jar / ART）提供的。所以我们不可能在 dex 里找到它的 `code_item` 去解释执行，只能在解释器里"桥接"：指令照常走 `invoke-virtual`，识别到类描述符是 `Ljava/lang/StringBuilder;` 就切到内核实现。

### 44.1 静态字段：`sget` / `sput`

`0x60` / `0x67`，21c 格式（AA 8 bit + field@BBBB 16 bit）。真实 DEX 里静态字段属于类的 `static_fields` 数组，要按类的 `static_fields_off` 定位；这里简化成一张 8 槽的全局表，直接用 `field_idx` 索引：

```rust
const NSFIELD: usize = 8;
static mut SFIELDS: [i32; NSFIELD] = [0; NSFIELD];
```

为什么可以直接按全局 field_idx 索引：fixture 里只有一个类有静态字段（`Main.hits`），索引不会撞。多类多静态字段就要按 `(class_idx, field_idx)` 分组，等真跑别人的 APK 再说。越界（`f >= 8`）报"静态字段槽越界"，不静默。

### 44.2 动态字符串槽

`toString()` 生成的是运行时字符串，**没有 string_idx 可用**——`string_ids` 是编译期固化的。所以另开一张槽表：

```rust
const DYN_TAG: i32 = 0x200;
static mut DYN: [[u8; 96]; 4];  static mut DYN_LEN: [usize; 4];
```

寄存器里的字符串值约定：`< 0x200` 是常量 `string_idx`，`>= 0x200` 是"动态字符串 `0x200+i`"。和数组的 `0x100+i` 区间错开。`str_of()` 把两种来源统一成一个 `&str`，`Log.i` 和 `append(String)` 都走它。

这个约定有真实风险：大 APK 的 `string_ids` 轻松超过 512 条，常量索引会撞进 `0x200` 段。当前 fixture 只有 30 来条，安全；要修就得换成"寄存器里存 `(kind, idx)` 打包"或独立字符串寄存器堆，属于 APK-10 级别的重构。

### 44.3 StringBuilder 内建

```rust
static mut SB: [u8; 128];  static mut SB_LEN: usize;
```

`<init>` 清空，`append` 追加，`toString` 把缓冲冻结成一个动态字符串槽并返回 `0x200+i`。三个方法都在内核侧，不进 `code_of`。

`append` 有两个重载（`(String)` 和 `(I)`），解释器用 `shorty` 的第二个字符区分：`"LL"` 是字符串参数、`"LI"` 是整数参数。`shorty` 是 DEX 里给校验器用的简化签名（返回类型 + 各参数的短名），这里正好当类型标签用，省得再去解 `proto_ids` 的 `parameters_off`。整数转十进制是手写的（no_std 没有 `itoa`）：取绝对值、逐位取余进 buf、再反转、负数补 `-`。

`append` 的返回值按 Java 语义返回 `this`（`args[0]`），虽然链式调用在 fixture 里没用到，但语义对了才不会在后面绊人。

### 44.4 fixture（第五版）

```java
static int hits;
static void run() {
    int[] a = new int[5];
    for (int i = 0; i < 5; i++) { a[i] = i * 3; sum += a[i]; }
    Log.n(sum);                       // 30
    hits = hits + 1;
    StringBuilder sb = new StringBuilder();
    sb.append("sum=");   sb.append(sum);
    sb.append(" hits="); sb.append(hits);
    Log.i(sb.toString());             // sum=30 hits=1
}
```

63 个 code unit，dex 1228 字节，`demo3.apk` 998 字节。实拍 `[DEX] 30` / `[DEX] array ok` / `[DEX] sum=30 hits=1`，65 条指令。

### 44.5 这次的坑

`invoke-virtual` 的 opcode 是 `0x6e`，我按"virtual 就是 76"写成了 `0x2076`，跑出来 `不支持的 opcode 0x76 @pc 41`。`0x76` 是 `invoke-direct/range`，不是 virtual。35c 格式里 unit0 是 `argc<<12 | G<<8 | op`，`G` 是第五个参数寄存器（这里不用），所以正确的 `invoke-virtual {v6,v0}, argc=2` 是 `0x206e`。

顺带把 `proto_ids` 的 `return_type_idx` 从字符串索引改成了真正的 `type_ids` 索引——之前那版写的是 `S_V`（字符串 "V" 的索引 18），而 `T_V` 才是 2。内核从不读 `return_type`，所以一直没暴露；这次既然要读 `shorty` 判类型，就顺手把这一栏改对了。

### 44.6 现状与下一步

`append` 只支持 `String` 和 `int` 两种重载。`append(char)`、`append(long)`、`append(Object)` 都没有；`StringBuilder` 只支持一个实例（缓冲是静态单份）；动态字符串槽只有 4 个、单个 96 字节。

这些限制都写在代码注释里。下一步是 `invoke-super` 与异常（`throw` / `try-catch` 的 handler 表），有了异常才能真正跑一个会失败、会 catch 的 APK；再往后是屏幕绘制桥接，把那 1024×768 的 framebuffer 从 `Log` 后面拉出来。

## 45. APK-8：继承与异常

到 APK-7 为止，解释器只会"直线执行 + 自己递归调用自己写的方法"。真实 APK 有两件事绕不开：**继承**（子类只声明自己新增的方法，其余上溯父类）和**异常**（构造器可能抛、库方法可能抛，handler 在别的帧里）。

### 45.1 方法解析上溯

`code_of` 原来只在本类里找同名方法。`Child extends Base` 时，`Child` 只有 `<init>`，`get()` 声明在 `Base` 上——`invoke-virtual {child}, Base.get()` 的 `method_id` 指向 `Base`，直接命中；但若代码写的是 `invoke-virtual` 且 `method_id` 指向 `Child`，就找不到。

改为沿 `superclass_idx` 链上溯，最多 4 层：

```rust
loop {
    match code_in_class(d, h, desc, name) {
        Ok(c) => return Ok(c),
        Err(e) if e != "没有这个类" => {
            let sup = u32le(d, class_def_pos(d, h, desc)? + 8);
            if sup == u32::MAX { return Err("类里没有这个方法（已到根类）"); }
            desc = type_desc(d, h, sup)?;
        }
        Err(e) => return Err(e),
    }
}
```

`superclass_idx = 0xFFFFFFFF` 表示根（`java.lang.Object` 我们没建模，就用 MAX 当根）。

### 45.2 `invoke-super`（0x6f）

格式与 `invoke-virtual` 相同（35c），差别只在语义：调父类的同名方法。因为我们不解 `method_id` 里"声明类"以外的信息，`0x6f` 直接并进同一分支，走 `code_of(m.class, m.name)`——`m.class` 本来就指向父类。

fixture 里 `Child.<init>(I)` 就是 `invoke-super {v0,v1}, Base.<init>(I)V`：子类构造器不自己写字段，交给父类写。`Base.<init>` 里 `iput v1, v0, field@2` 把 7 写进对象的字段槽，`Base.get()` 再 `iget` 出来。实拍 `[DEX] 7`，证明整条链（构造器 → 字段 → 继承方法解析）都通了。

### 45.3 异常：一条哨兵错误 + 一张 try 表

不引入 `enum Flow`，也不重写 exec 的返回类型。做法是：

- 一个全局 `THROW_VAL: i32` 存异常对象引用；
- 一条哨兵错误串 `"__aster_throw"` 当"这是异常不是程序错误"的标记；
- `throw vAA`：写 `THROW_VAL`，在本方法里找 handler，找到就 `pc = handler`，找不到 `return Err(哨兵)`；
- 遇到子调用时用 `match` 而不是 `?`：`Err(哨兵)` 就先查本方法在该**调用指令 pc** 上的 handler，接住就跳过去；查不到就继续往上抛；
- `move-exception vAA`（0x0d）：把 `THROW_VAL` 放进寄存器，handler 第一条指令通常就是它。

`find_handler` 读 `code_item` 的 `tries_size`：

```
insns[insns_size]        （奇数条时要 2 字节对齐填充）
try_item[tries_size]     { u32 start_addr; u16 insn_count; u16 handler_off; }
encoded_catch_handler_list
```

`handler_off` 相对 handler 列表起点，`encoded_catch_handler` 的 size 是 **sleb128**（有符号），`<= 0` 表示含 catch-all。我们只取第一个地址，不做异常类型匹配——catch-all 就够 demo。

### 45.4 fixture（第六版）

```java
class Base { int v; Base(int x){v=x;} int get(){return v;} }
class Child extends Base { Child(int x){ super(x); } }
class Boom { Boom() { throw new RuntimeException(); } }

static void run() {
    ... // 数组、静态字段、StringBuilder（APK-6/7 全部保留）
    Child c = new Child(7);
    Log.n(c.get());                              // 7
    try { new Boom(); } catch (Throwable t) { Log.i("caught xmethod"); }
    try { throw new RuntimeException(); } catch (Throwable t) { Log.i("caught local"); }
    Log.i("apk8 ok");
}
```

101 个 code unit，两张 try 表（`[75,80)` 覆盖 `Boom.<init>` 调用、`[86,89)` 覆盖本地 `throw`），两个 catch-all handler。dex 1860 字节，`demo3.apk` 1264 字节。实拍：

```
[DEX] 30
[DEX] array ok
[DEX] sum=30 hits=1
[DEX] 7
[DEX] caught xmethod
[DEX] caught local
[DEX] apk8 ok
run() 执行完（90 条指令），正常 return-void
```

`caught xmethod` 是跨方法传播：异常在 `Boom.<init>` 里抛，`run` 在调用指令 pc 上接住。`caught local` 是同方法抛出、同方法 handler。

### 45.5 这次的两个坑

**一、`const/4` 又写反一次。** `const/4 v5, #7` 应该是 `0x7512`（lit 7 在高 4 位），我写成 `0x3512`（lit 3），于是 `Child(7)` 变成 `Child(3)`，`get()` 打出 3。上一轮刚记录过这条，说明"记住"不等于"不犯"，唯一的防线是反汇编自检——现在 `mkdex.py` 每次生成都会打印每个 code_item 的 code unit，`0x3512` 一眼就能对上 `v5=3`。

**二、`info` 字典漏键导致 apk 静默不更新。** `main()` 里回填 header 前会遍历 `("code_init", ..., "code_boom_init")` 读 `info[name]`，我加了 code_item 却忘了把这个键塞进 `info`，于是 `KeyError` 抛在写 zip 之前——**`demo3.apk` 一直是上一版**，而内核也一直编译同一个 1860→1682 的旧包，跑出来全是旧输出。这个坑比代码 bug 更阴：脚本"看起来跑了"（前半段反汇编照样打印），只有最后一行 `demo3.apk ... bytes` 消失。所以现在的判断标准是**看最后那行字节数**，看不到就是没写成功。

### 45.6 限制

- 不做异常类型匹配：`catch (IOException)` 和 `catch (Throwable)` 一样处理，永远走第一个 handler 地址。
- 只有 catch-all 和"第一个 typed handler"两种解码路径，多 handler 的 `encoded_catch_handler` 链没走完（size 为负时的 typed 部分被跳过）。
- 异常对象不带堆栈、不带 message（`new RuntimeException("x")` 的 `<init>(String)` 会找不到方法）。
- 方法解析最多 4 层父类；接口（`interfaces_off`）完全没解。
- `finally` 没有专门支持（DEX 里它被编译成"catch-all + 重抛"，理论上现在就能跑，但没测）。

下一步是**屏幕绘制桥接**：把 `Log.i` 之后的东西拉到 framebuffer 上——`Canvas`/`View` 那一套太重，先做 `Paint`/`drawText`/`drawRect` 三个内建，让 APK 能往屏幕上写一行字、一个方块。那才是"能跑 APK"在用户眼里的样子。

## 46. APK-9：画布桥接

到 APK-8 为止，APK 的可见输出只有串口里的 `[DEX] ...`。用户眼里"能跑 APK"不是这个——是屏幕上出现东西。这一站把 `Log` 后面的画布拉出来。

`android.graphics.Canvas` / `Paint` / `View` 那套太重（要 `Bitmap`、要 `Path`、要 `View` 树和 `Choreographer`），先做自研的最小画布：`Lcom/aster/Canvas;`，四个方法。

### 46.1 不分配位图，只记命令

`kernel/src/apkcanvas.rs`：不申请像素缓冲，而是记一份**绘制命令表**，每次桌面重绘时按 2 倍缩放叠到屏幕中央。

```rust
struct Cmd { kind: u8, x: i32, y: i32, w: i32, h: i32, color: u32, slot: usize }
static mut CMDS: [Cmd; 48];  static mut NC: usize;
static mut STRS: [[u8; 48]; 12];  // 文字就地复制，避免跨模块借字符串
```

为什么不做真位图：位图要按需分配（`alloc` 或页帧），而画布一旦是离屏缓冲，还要有"合成到屏幕"的搬图路径和 320×200→1024×768 的拉伸。命令表这个做法在 demo 规模上零成本，而且**天然适配桌面重绘**——每次 `render_dashboard()` 末尾重放一遍就行，不需要管脏区。

### 46.2 四个方法

| 方法 | 编码 | 语义 |
|---|---|---|
| `<init>()V` | 35c | 清命令、清文字槽、置 `ACTIVE` |
| `clear(I)V` | 35c | 换底色并清掉已有命令 |
| `setColor(I)V` | 35c | 设当前画笔色，影响后续 rect/text |
| `drawRect(IIII)V` | 35c argc=5 | `x,y,w,h`，用当前色 |
| `drawText(String,II)V` | 35c argc=4 | `x,y` 画一行字，字号是画布的 2 倍放大 |

`drawRect` 要 5 个寄存器（canvas + 4 个 int），正好用满 35c 的 `C/D/E/F/G`——`G` 在 unit0 的 bits 8-11，这也是第一次把第 5 个参数寄存器用上。

`draw_if_active()` 的落点：`shell::render_dashboard()` 最后一行。桌面每次重绘（光标闪烁、鼠标、终端输出）之后都把画布重放一遍，所以画布不会被刷掉。

### 46.3 fixture（第七版）

```java
Canvas cv = new Canvas();
cv.clear(0x101418);
cv.setColor(0x5b99ff); cv.drawRect(20, 20, 60, 8);          // 标题下划线
cv.setColor(0xdadde2); cv.drawText("Aster APK", 20, 48);
cv.setColor(0x46c46a);
cv.drawRect(20, 80, 40, 40); cv.drawRect(70, 80, 40, 40); cv.drawRect(120, 80, 40, 40);
Log.i("canvas ok");
```

176 个 code unit，dex 2276 字节，`demo3.apk` 1465 字节。实拍：画布浮在桌面之上，蓝色下划线 + 灰白标题 + 三个绿色方块，底边一小行 `APK Canvas 320x200` 标记。`canvas` / `canvas off` / `canvas on` 可以收起/放回。

### 46.4 这次的三个坑

**一、`const`（31i）根本没实现。** 前六版 fixture 的常量都在 `const/4`（−8..7）和 `const/16` 范围内，所以从没碰过 32 位常量；一写颜色 `0x5b99ff` 立刻 `不支持的 opcode 0x14 @pc 105`。补上 `0x14`：`(hi<<16)|lo`。

**二、`invoke-virtual` 的 argc 少了 `this`。** `clear(I)V` 我写成 `0x106e`（argc=1），于是 `args[1]` 从没被赋值，恒为 0——`clear(0)` 把底色画成纯黑、`setColor(0)` 让所有图形变黑。表现是"画布是黑块、内容全看不到"。正确是 `0x206e`（this + 1 个 int）。`drawRect` 的 `0x576e`、`drawText` 的 `0x406e` 都是 argc 对上的，所以只有这两个方法坏——**同一个 API 里一半对一半错，最容易误判成"画布渲染有问题"**。

**三、32 位常量的高低 16 位写反。** `0xdadde2` 写成 `0x0514, 0x0dde, 0x00da`，拼出来是 `0x00da0dde`（R=da,G=0d,B=de），屏幕上标题变成洋红色。改成 `0xdde2, 0x00da` 才回到灰白。这个错误特别像"颜色通道反了"，很容易跑去改 `fb::native()`——实际上 `native()` 是恒等函数，通道一直是对的。

另外记一条工程教训：**改 `assets/*.apk` 后 `make image` 经常不重编**（`include_bytes!` 的依赖检测不稳），可靠做法是 `cd kernel && cargo clean -q`。这轮在这上面浪费了三次"改了没效果"。

### 46.5 限制与下一步

- 画布坐标固定 320×200、固定 2 倍、固定在屏幕中央；没有多窗口、没有 DPI 概念。
- 命令表 48 条、文字 12 条各 48 字节，超了静默丢弃（`stats()` 里能读到丢弃数）。
- `drawRect` 是实心填充，没有描边、没有圆角、没有透明度。
- 没有读回像素（`getPixel`）、没有 `save/restore`、没有裁剪。
- 文字只能画一行、不换行、不测量宽度（`text_len` 没接出去）。

下一步有两条：一是**触摸/点击事件回传给 APK**（现在画布是只读的，点了没反应）；二是**放开 `new-array`/位图的上限**，把页帧分配器给用户态开个口子——那才是能跑真实 APK 的地基。前者成本低、体验增益大，建议先做。

## 47. APK-10：画布点击回传

画布在 APK-9 里是"只读"的：能画，点了没反应。这一节把指针事件接回虚拟机。

### 47.1 内核侧

`kernel/src/apkcanvas.rs` 加了一个 8 深的环形队列 `TQ: [(i32, i32, bool); 8]`，配 `TQN`（写入总数）/`TQR`（读游标）/`LASTT`（最后一次按下的画布坐标）。

```rust
pub fn origin() -> (i32, i32)          // 画布左上角在屏幕上的坐标
pub fn screen_to_canvas(sx, sy) -> Option<(i32, i32)>   // 屏幕点 -> 画布坐标，越界返回 None
pub fn push_touch(cx, cy, down)
pub fn take_touch() -> Option<(i32, i32)>   // 只取按下事件，记进 LASTT
pub fn last_touch() -> (i32, i32)
```

`ui::handle_mouse()` 在 `take_click()` 循环的**最前面**拦一道：只要画布是 active，且落点在 `origin()` + 640×400 之内，就把这个点换算成画布坐标压进队列并 `continue`——**它不会再落到桌面上当"点窗口"处理**。抬起的那个事件也压进队列，但 `take_touch()` 只取 `down`，避免一次点击被读两遍。

`dex.rs` 的 `Lcom/aster/Canvas;` 分支加两个内建方法：

- `touchX()I` — 取一次队列里的按下事件，有就返回画布坐标 x，没有返回 `-1`；顺带把坐标记进 `LASTT`。
- `touchY()I` — 返回 `last_touch().1`。

所以 APK 侧的惯用法是"先问 `touchX()`，非负再问 `touchY()`"。

### 47.2 fixture 第八版

`tools/mkdex.py` 的 `code_run` 末尾追加（pc 175 起，41 条指令，总 216 code unit）：

```
int tx = cv.touchX();
if (tx >= 0) {
    int ty = cv.touchY();
    cv.setColor(0xd9a441);
    cv.drawRect(tx - 4, ty - 4, 8, 8);
    Log.i("touch hit");
} else {
    Log.i("no touch");
}
```

dex 2424 字节，`demo3.apk` 1551 字节。实拍：先 `canvas on` 让画布成为命中区，`sim click 400 400`（屏幕点 → 画布 `(104,108)`），再 `dex run`，光标处立刻多出一个金色 8×8 标记，串口 `touch hit`、137 条指令；不点时输出 `no touch`、126 条指令。

### 47.3 这轮踩到的四个坑

**一、内建分支末尾多了一行 `last = 0`。** `Canvas` 的 `clear/setColor/drawRect/drawText` 都是 void，我当初在 match 之后统一写了 `last = 0` 当作"清返回值"，结果 `touchX` 算出来的 `-1`/坐标在 `move-result` 之前就被抹成 0——APK 里 `if (tx >= 0)` 恒真，不点也走"命中"分支。删掉那行即可（`last` 本来就是上一次调用的返回值，不该由调用方清）。

**二、23x 格式的单元字节序。** `sub-int vAA, vBB, vCC` 的第二单元是 `CC|BB`（**低字节 BB、高字节 CC**），我按"高 BB 低 CC"写了 `0x0400`，`v5 = v4 - v0 = -100`，方块被裁到画布外面，看起来"完全没画"。内核当前的取法是 `b = w >> 8`、`c = w & 0xff`，所以 fixture 必须按 **`BB<<8|CC`** 写：`sub-int v5, v0, v4` → `0x0004`。

**三、第二次 `move-result` 写错了目标寄存器。** `touchY()` 之后我图省事复用了 `0x000a`（move-result v0），但 y 应该进 `v3`。于是 `sub-int v3, v3, v4` 减的是一个循环残留值 120，方块被画到 y=116——离点击点 8 像素，看上去像"命中位置偏了"。正确是 `0x030a`。

**四、截图撕裂。** 命中画布会让 `want = true`，UI 连续重绘几帧；ramfb 在 `-display none` 下抓 `screendump` 正好赶上中间态，出现"整窗空白""只剩标题条"的假故障。判据是串口：日志里 `touch hit` 已经打出，画面不对就多补两条 `uptime` 让 UI 多刷几帧再截。

### 47.4 限制

- 队列 8 深、只保留按下事件；拖动（move）没有转给 APK，`touchMove` 还不存在。
- 坐标是画布像素，没有压力、没有多点、没有时间戳。
- 画布仍然固定 320×200 / 2 倍 / 居中；命中区跟着 `origin()` 走，但 APK 自己不知道画布尺寸（没有 `width()`/`height()`）。
- 无显示环境（`-nographic`）下 `ui::tick` 不消费指针，`make test` 只能断言"无事件返回 -1"，命中路径靠图形截图取证（`build/apk10t.png`）。

## 48. APK-11：驻留 app（帧回调 + 拖动）

到 APK-10 为止，`dex run` 还是"跑完一个方法就退出"的脚本模型：画一次图，然后进程结束，Dex 状态全丢。这一节把它改成**能一直活着、每帧重画、跟着手指走**的 app。

### 48.1 事件模型

`apkcanvas` 的触摸队列从"一个 (x, y, down) 环形队列"拆成两条：

| 队列 | 深度 | 语义 | 对应 API |
|---|---|---|---|
| `DQ` | 8 | 按下点（抬起丢弃） | `touchX()` / `touchY()` |
| `MQ` | 8 | 拖动点（满了丢最老的，永远留最新） | `moveX()` / `moveY()` |

分开的理由很直白：**按下是离散事件不能丢，拖动是连续状态丢掉旧的正好**。混在一个队列里，APK 一帧取一次就只能看到 1/6 的拖动轨迹，方块会抽搐。

`ui::handle_mouse()` 里新增一段：画布 active 且左键按住、鼠标位置相对上一拍有变化 → `push_move(换算后的画布坐标)`。抬起或指针移出画布就清空"上一拍位置"，下次按下重新开始。

### 48.2 帧回调

shell 里保存三件事：`APP_ON`、`APP_FRAMES`，dex 数据则每帧从 `INFL_BUF` 现取（`zip::extract` 是 stored 条目，2.8 KiB 拷贝，代价可以忽略，好处是不用操心生命周期）。

```rust
pub fn app_active() -> bool
pub fn app_frame() -> Option<&'static str>   // None = 这一帧跑成功
```

`ui::tick()` 里每 30 ms 调一次 `app_frame()`：

```rust
if crate::shell::app_active() {
    let now = timer::now_ms();
    if now.saturating_sub(APP_MS) >= 30 {
        APP_MS = now;
        if crate::shell::app_frame().is_some() { want = true; }  // 出错就不再重绘
    }
}
```

`app_frame()` 的流程是：`apkcanvas::reset()` → `zip::extract` → `header` → `dex::app_step("Main", "frame")`。**关键在 `reset()`**：每帧从空命令表开始画，APK 画什么就是什么；否则上一帧的命令会叠上来，48 条槽很快塞满。

失败即停机：`app_frame` 把错误串返回给 UI，同时把 `APP_ON` 置 false，避免同一个错误每 30 ms 刷一次屏幕。

dex 侧新增两个入口：

- `app_begin(d, h, class)`：清对象堆、清静态字段、**装 static_values 初值**、确认 `frame()` 存在。起动时调一次。
- `app_step(d, h, class, name)`：只 `exec`，不重置任何状态——静态字段和对象堆跨帧活着，这才是 app。

`Canvas.<init>` 仍然是 `reset + set_active(true)`，所以 APK 第一帧建完 Canvas 之后就一直有画布。

### 48.3 静态字段初值（static_values）

这一版第一次用到 `class_def.static_values_off`：DEX 的静态字段初值不在 `field_ids` 里，而是在类定义指向的一个 `encoded_array` 中，**按 class_data 里静态字段的声明顺序**一一对应。

`load_statics()` 做的事：读 class_data 拿到静态字段的 field_idx 列表 → 读 encoded_array → 逐个写进 `SFIELDS`。值类型只认 `VALUE_INT`（`0x04`），`value_arg` 是"字节数 − 1"。

fixture 里 `cvh = 0, hits = 1, px = 140, py = 80`，于是 app 一启动方块就在画面中间偏左，而不是从 (0,0) 角落爬出来。

### 48.4 fixture 第九版

`tools/mkdex.py` 新增 `Main.frame()V`（107 code unit，dex 2818 字节，`demo3.apk` 1767 字节）：

```
static int cvh, px = 140, py = 80;
static void frame() {
    if (cvh == 0) cvh = new Canvas();
    Canvas c = cvh;                  // 解释器里对象引用就是堆索引，直接 sget 出来当 this 用
    c.clear(0x101418);
    c.setColor(0x5b99ff); c.drawRect(16, 16, 40, 4);
    c.setColor(0xdadde2); c.drawText("Aster APK", 16, 36);
    c.setColor(0x46c46a); c.drawRect(px, py, 32, 32);
    int mx = c.moveX();  if (mx >= 0) { px = mx - 16; py = c.moveY() - 16; }
    int tx = c.touchX(); if (tx >= 0) { px = tx - 16; py = c.touchY() - 16; }
}
```

Canvas 句柄存进静态字段是这版的一个小技巧：`new-instance` 只跑第一帧（`if (cvh == 0)`），之后每帧 `sget v6, cvh` 拿同一个堆索引当 `this` 传给 `invoke-virtual`。解释器不检查类型，对象引用本来就是 i32 的堆索引，所以这条路畅通——也意味着**对象堆只有 8 个槽，app 要是每帧 new 一个对象就会在 8 帧后爆掉**，这是明确的 demo 级限制。

实拍三张：

1. `app start` → 蓝下划线 + 灰白标题 + 绿方块在 (140,80)，`app status` 报 "已画 54 帧，命令 3 条"。
2. `app start` + `sim drag 400 400 → 620 470` → 方块跟到光标处（画布 (198,127)），79 帧。
3. `app start` + `sim click 500 300` → 方块跳到点击点（画布 (138,42)），101 帧。

### 48.5 这轮踩到的四个坑

**一、每帧忘了清命令表。** 第一版 `app_frame` 直接 `app_step`，于是命令累积到 48 条上限，`app status` 打出"命令 2 条（丢弃 42）"——画面只留下最初几笔，剩下全被丢掉。判据是 `DROPPED` 不为 0。修法就是每帧 `reset()`。

**二、`add-int/lit8` 的 22b 单元字节序。** 我按 `lit<<8 | BB` 写 `0xF000`，内核读出来的 BB 是 240，`regs[240]` 直接越界 panic（`dex.rs:850`）。正确是 `BB<<8 | lit`：`add-int/lit8 v3, v0, #-16` → `0x00F0`（BB=0，lit=0xF0=−16）。

**三、`VALUE_INT` 是带符号的。** `px = 140` 我写成单字节 `0x04 0x8c`，解析时按 8 位符号扩展成 **−116**，方块被画到画布外，屏幕上什么都看不到。要写正数就得给两个字节：`0x24 0x8c 0x00`（value_arg=1）。同类错误在 `const/4`、`const/16` 上都踩过，这次轮到了 encoded_value。

**四、连续重绘导致截图撕裂。** app 跑着的时候 UI 每 70 ms 重绘一次，`screendump` 大概率抓到中间态：整窗空白、只剩标题条、画布一块纯色。取证套路是 `app stop` 之后再补两条 `uptime` 静置，画面就稳了。**别把撕裂当成绘制 bug 去改 `apkcanvas`。**

### 48.6 限制

- 帧率受 UI 的 70 ms 重绘节流限制，实际 ~14 fps；没有脏矩形，每帧整块画布重画。
- 没有 `onCreate`/`onPause`/`onDestroy`，只有 `frame()`；也没有 `stop` 通知给 APK（停就是内核侧不调了）。
- 拖动没有速度/加速度，坐标一步到位；没有多点、没有压力。
- 对象堆 8 槽、数组 4 槽、动态字符串 4 槽、StringBuilder 单实例，全是 demo 规模。
- 画布固定 320×200 / 2 倍；`width()/height()` 已经能自报尺寸，但不支持改。
- `app` 只认内嵌的 `demo3.apk`，还不能从 AsterFS 选包。

### 48.7 下一步

到这里"APK 能画、能点、能拖、能活着"四件都齐了。下一站建议是**把画布让给真正的 Activity 语义**：`onCreate` 一次、`frame` 循环、`onTouch` 事件分发，再加上 `Intent` 那种最简的启动参数——这是"跑真实 APK"的最后一块拼图。同时顺手把 `new-array`/对象堆的上限放开（页帧分配器已经就绪，缺的只是把它接给解释器）。

## 49. APK-12：Activity 生命周期与事件分发

APK-11 里 APK 是"自己轮询"的：每帧问一次 `moveX()`。这节把它翻过来——**内核主动调 APK**，生命周与事件分发都由内核驱动，APK 只实现回调。

### 49.1 三个回调

| 回调 | 何时 | 签名 |
|---|---|---|
| `onCreate` | `app start` 一次 | `()V` |
| `frame` | 每 30 ms | `()V` |
| `onTouch` | 事件到达时 | `(III)V`，kind 0=按下 1=拖动 2=抬起 |
| `onDestroy` | `app stop` | `()V` |

`onCreate` / `onDestroy` 是可选的：`dex::has_method()` 用 `code_of` 试一下，没有就跳过。`frame` 是必需的，没有直接报错。

`app start` 的流程变成：`heap_reset` → `call_reset` → `load_statics`（装初值）→ `onCreate` → 校验 `frame` 存在。`app stop` 先调 `onDestroy`，再把 `APP_ON` 置 false。

### 49.2 事件队列统一

APK-11 的 down / move 双队列合并成一条 `EV: [(x, y, kind); 16]`，三条取法：

- `next_event()` — FIFO 全取，供 `onTouch` 分发
- `take_touch()` / `take_move()` — 扫描队列挑出对应 kind 的那条，保留老的 `touchX()` / `moveX()` API（对 APK-10/11 的写法兼容）

队列满（16 条）时丢最老的。`push_touch` 现在把**抬起**也入队（kind 2），因为 `onTouch` 需要它。

`shell::app_frame()` 每 30 ms 做两件事：先把队列里所有事件 `dex::app_touch(kind, x, y)` 投递掉，再 `apkcanvas::reset()` + `app_step("frame")`。一次事件一次 `exec`，最多 16 次/拍，代价可接受。

### 49.3 上限放开

demo 级限制在这节统一往上抬一档：

| 资源 | APK-11 | APK-12 |
|---|---|---|
| 对象堆 | 8 | 32 |
| 数组槽 | 4 | 16 |
| 单数组长度 | 8 | 32 |
| 画布命令 | 48 | 128 |
| 文字槽 | 12 | 32 |
| 事件队列 | 8 + 8（分开） | 16（合一） |

内存代价很小（对象堆 32×8 个 i32 ≈ 1 KiB，数组 16×33 个 i32 ≈ 2 KiB），但"8 帧就爆"的坑没了。

### 49.4 fixture 第十版

`Main` 现在有 5 个静态字段（`cvh`、`hits`、`px`、`py`、`taps`）、6 个 direct 方法（`run`、`hello`、`frame`、`onCreate`、`onTouch`、`onDestroy`），dex 3118 字节、`demo3.apk` 1896 字节。

```java
static void onCreate() { cvh = new Canvas(); Log.i("onCreate ok"); }
static void frame() { /* 画背景/标题/方块，107 code unit */ }
static void onTouch(int kind, int x, int y) {
    if (kind > 1) { Log.n(taps); return; }   // 抬起：报累计次数
    px = x - 16; py = y - 16; taps++;
    Log.n(taps);
}
static void onDestroy() { Log.i("onDestroy ok"); }
```

实拍：`app start` 打 `[DEX] onCreate ok` 并报 "已画 53 帧，命令 3 条（丢弃 0）"；`sim drag 400 400 → 600 460` 期间串口连续 `[DEX] 4..9`（每一步触摸都进了 `onTouch`），方块最终落在 (188,122)；`app stop` 打 `[DEX] onDestroy ok` 并报 "onDestroy 已调用"。

### 49.5 这轮唯一的大坑：`ins_size` 的参数位置

DEX 的方法参数**不放在 v0 开始**，而是放在寄存器窗口的**最后 `ins_size` 个**。`onTouch(III)V` 的 `regs_size=4, ins_size=3`，于是 `kind→v1`、`x→v2`、`y→v3`，**v0 是空闲临时寄存器**。

第一版我按 `v0=kind, v1=x, v2=y` 写，结果是：`if-gt v0, v3` 拿未初始化的 v0 去比 y，`add-int/lit8 v1` 减的是 kind。表现很诡异——日志里 taps 稳定递增（说明 `onTouch` 确实被调用了、`sput` 生效），但方块完全不动（`px/py` 被写进错误的位置）。

顺带一个小坑：`if-gt` 的 22t 编码里 **A 在 bits8-11、B 在 bits12-15**，我写成 `0x0035` 等于 A=B=v0，`v0 > v0` 恒 false，条件分支静默失效。正确是 `0x1035`（A=v1, B=v0）。

这已经是这个项目里第 N 次被 DEX 的"寄存器窗口"绊倒了：**实例方法第一个参数是 this 也在这个窗口里**，`invoke-virtual` 的 argc 同样含 this。写 fixture 时的第一条自检应该是"我要用的参数到底落在哪几个寄存器"。

### 49.6 限制

- 没有 `onPause` / `onResume` / `onRestart`：只有 create → frame… → destroy。
- `onTouch` 没有事件时间戳、没有 `MotionEvent` 的 action 位掩码，kind 是简化后的三态。
- 没有手势识别（点击 vs 拖动的判定在 APK 侧自己做）。
- 仍然是单实例、单类 `Main`；没有 `Intent`、没有 `startActivity`。
- 对象堆 32 槽仍是固定的：真实 APK 每帧 new 对象就会溢出，必须有 GC 或页帧分配器接进来。

### 49.7 下一步

"能跑自制子集 APK"这条路，只差最后两块：**Intent 化启动**（`app start <参数>` 把参数塞给 APK，`App.arg()` 取回）和**对象分配接到页帧分配器**（现在 32 槽静态堆是硬顶）。之后才是 `android.graphics` 真实 API 的映射，那是另一个量级的工作。

## 50. APK-13：对象堆接到页帧分配器 + 启动参数

APK-12 的对象堆是 `static mut HEAP: [ObjState; 32]`，跑几十帧就撞顶。这一节把它换成**真内存**：对象槽由页帧分配器按 4 KiB 页供给，跨页用链串起来。同时给 APK 一条拿到启动参数的窄通道。

### 50.1 页与槽的布局

一页 4096 字节，页头 64 字节，后面 63 个 64 字节槽：

```
页头（64 B）                槽（64 B）
+0  next   u64  下一页        +0   used      u32  0=空 1=活
+8  nslot  u16  本页槽数       +4   class_idx u32
+10 used   u16  本页已用       +8   pad       8 B
+12 ~63 保留                  +16  fields    [i32; 8]
                             +48  余量 16 B（monitor / refcount / GC 标记）
```

63 × 64 + 64 = 4096，一页正好装满，不浪费。页头留 52 字节余量是给将来变长槽和 mark 位图用的。

`HEAP_HEAD` 是页链头，`HEAP_TAIL` 是链尾——新页直接接在尾巴上，扩页是 O(1)；`page_at(n)` 才走链，n 通常 ≤ 2，代价可忽略。

`frame::alloc()` 分配的页一律清零，所以槽的 `used=0` 天然成立，不用额外初始化。

### 50.2 引用值的 tag 重新划分

原来的引用是 0..32 的小整数，和数组 `0x100+i`、动态字符串 `0x200+i`、常量 string_idx 挤在一起。堆变大之后槽号会过千，必须重划：

| 区间 | 含义 |
|---|---|
| `0` | null |
| `0 .. 0xFFFF` | 常量字符串（string_idx） |
| `ARR_TAG+i` = `0x100+i` | 数组槽 |
| `DYN_TAG+i` = `0x200+i` | 运行时拼出来的字符串 |
| `OBJ_TAG+g` = `0x1_0000+g` | 对象（g 是全局槽号） |

`str_of()` 也相应加了上界判断：`v >= DYN_TAG && v < OBJ_TAG` 才算动态字符串，对象引用不会再被误当字符串解析。

### 50.3 分配与回收

`heap_new(class_idx)` 取 `HEAP_GIDX`（单调递增的全局槽号），必要时 `grow_pages(g / 63)` 补页，然后写 `used/class_idx/fields`。返回 `OBJ_TAG + g`。

**没有单个释放**：`heap_reset()` 把整条页链逐页 `frame::free()` 还给池子，`HEAP_GIDX` 归零。所以它是"整堆重置 + 只增分配"，不是 GC。这是刻意的——先把分配路径做对，回收策略（引用计数或 mark-sweep）留到有真实 APK 压测时再定。

`shell` 的 `app status` 直接报三个数：

```
[APP] 对象堆 2 页 / 槽 71 用 71（容量 126）
```

fixture 第十一版在 `onCreate` 里连开 70 个 `Counter`，71 个对象必然跨到第二页；底栏的 `页帧 2` 是同一件事的独立证据（页帧分配器被真的动了 2 页）。

### 50.4 启动参数

`app start <n>` 把 n 存进 `dex::START_ARG`，APK 侧用内建 `Lcom/aster/App;->arg()I` 取回。

语义故意做到最窄：一个 i32，没有 Bundle、没有 key、没有 Intent 对象。`onCreate` 里 `if (arg > 0) px = arg` —— 于是 `app start 40` 让绿方块从默认 140 移到 40。

这是 Intent 的第一层皮。真正的 `Intent`/`getIntent()`/`getExtras()` 要等能解析 `Bundle` 的 AXML 之后再说。

### 50.5 顺手修掉的三个陈年错

这一轮被 DEX 的编码规则又绊了三次，都属于"早就写在纸上但写 fixture 时手滑"：

1. **if 系列整体错位一位**。内核原来 `0x31..=0x36` 映射 if-eq..if-le，而规范是 `0x32..=0x37`（0x31 是 cmp-long）。因为 fixture 和内核一起错，内部自洽，所以一直没暴露。这次跑真 APK 前必须先对齐，已改成规范的 `0x32..=0x37`。
2. **`goto` 是 10t 单字格式**。偏移就在指令字自己的高字节（`0xF5<<8 | 0x28`），不是"两个字、偏移在第二字"。我照 22t 的写法给它配了一个 `0xFFF7` 的第二字，结果偏移被读成 −1、跳回自己、原地死循环。
3. **`add-int/lit8` 的 `BB`（源寄存器）不能省**。写成 `0x0100` 只有 lit=1 没有源寄存器，等价于 `v2 = v0 + 0`；得写 `0x0201` 才是 `v2 = v2 + 1`。表现是循环体只跑一次就退出。

另外 `frame` 里的 `if-eqz cvh` 是反的——该用 `if-nez`（非 0 才跳过创建）。这个错在静态 32 槽堆下表现为"每帧 new 一个 Canvas、32 帧后堆满"，被上一轮的上限放开掩盖过一次，这次因为 `app status` 会报槽数才被抓出来：128 帧 199 槽，差值正好等于帧数。

### 50.6 保险丝：单次调用指令上限

`exec()` 加了一条硬上限 `STEP_LIMIT = 200_000` 条指令。超了返回 `"执行超过指令上限（疑似死循环）"` 并打印当前 pc，而不是把内核转死。这一节所有死循环都是靠它定位的（看 pc 停在哪个值，就知道是 goto 还是分支的偏移算错）。

真 APK 的一帧远低于 20 万条，这个值暂时不需要做成可配置。

### 50.7 限制

- 没有单个释放，只有整堆还页：长时间运行会一路吃内存，直到页帧池耗尽报错。
- 页头 52 字节余量、槽 48 字节余量都还没用，是给 GC/monitor 留的位置。
- 一个对象固定 8 个 i32 字段，不看 `class_def` 里声明的实例字段数，也不支持 long/double/引用类型字段（全是 i32）。
- 数组仍是 `NARR=16` 个槽 × 32 元素，没用页帧；它比对象堆更早成为瓶颈。
- 启动参数只有一个 i32。

### 50.8 下一步

对象堆已经是真内存了，下一个瓶颈很明确：**数组也要接到页帧上**，否则 `new int[100]` 一律被拒。之后才是 `String` 的方法族和 `android.graphics` 的映射。

## 51. APK-14：数组也接到页帧分配器

APK-6 的数组是 `Arr { len, d: [i32; 32] }`，16 个槽、每个固定 32 元素。`new int[100]` 一律被拒——比对象堆更早成为瓶颈。这一节把元素本身放进页帧。

### 51.1 槽与元素分开

```rust
struct ArrSlot {
    used: bool,
    len: u32,      // 元素数
    npages: u16,   // 占几页
    data: u64,     // 元素缓冲区首页地址（恒等映射，可直接读写）
}
```

64 个槽 + `data` 指向一段**连续物理页**。元素是挨着的 i32，`aget`/`aput` 直接 `data + k*4`：

```rust
regs[a] = rd_i32(base + k as u64 * 4);
```

不再有"每个数组自带 32 个格子"这种浪费，小数组只占 4 字节 × n，大数组按需占页。

### 51.2 分配与回收

`arr_new(len)`：算出 `npages = ceil(len*4 / 4096)`，用 `frame::alloc_pages(npages)` 拿**连续**页（页帧分配器本来就支持连续分配，做 DMA 缓冲时写的）。`len=0` 不占页。

槽位用"扫描找空位"，所以数组能复用被释放的槽，不像对象堆那样只增。找不到空槽时把刚分配的页整段 `frame::free` 还回去再报错——不在失败路径上漏页。

`arr_reset()` 遍历所有 used 槽，按 `npages` 逐页 `free`。槽表本身是 `[ArrSlot; 64]`（64 × 16 B ≈ 1 KiB），还没到需要业主页的程度。

单数组上限 `MAX_ELEMS = 4096`（16 KiB / 4 页）。这不是内存限制，而是防一个 `new int[100000]` 把连续页吃光。

### 51.3 fixture 第十二版

新增 `Main.big()V`：

```java
int n = 2048;              // 8192 字节 → 2 页
int[] a = new int[n];
int s = 0;
for (int i = 0; i < n; i++) { a[i] = i; s += a[i]; }
Log.n(s);                  // 8386560? 不，2048 个元素求和 = 2096128
```

实拍：`[DEX] 2096128`、`[DEX] big ok`、`big() 执行完（28690 条指令）`；底栏与系统面板同时显示 **`页帧 2`**——两页正是 8192 字节元素缓冲区，和 `dex big` 之前是 0 页形成对照。

`make test` 的串里加了 `dex big`，断言 `[DEX] 2096128`：**26 项 PASS**。

### 51.4 这轮的坑：23x 的 A 是 8 位，不是 4 位

`aget vA, vB, vC` 的格式是 `AA|op`——**A 占 8 位**（不像 12x/22c/35c 那样只占 4 位）。我按"4 位"的习惯写了 `0x1444` 想表达 `aget v4, v0, v2`，实际被解释成 **A=0x14=20**，`regs[20]` 直接越界 panic：

```
!!! ASTER 内核 panic !!!
  位置: src/dex.rs:852
```

正确的是 `0x0444`。同一个 format 的 `aput`、`add-int`/`sub-int`（`0x90..0x94`）都是 8 位 A，写 fixture 时只要看到 `0x??` 后面跟 `op` 就要先问"这个 A 是 4 位还是 8 位"。

另外记一条**内核约定与规范的差异**：23x 的 unit1，规范是 `CC | BB<<8`（B 在高字节），内核读的是 `b = w & 0xff; c = (w>>8) & 0xff`（B 在低字节）。fixture 和内核一起错、内部自洽，所以一直能跑；但这是跑真 APK 前必须校正的一处，已记进待办。

### 51.5 限制

- 元素只有 i32：没有 `long[]`/`double[]`/对象数组（引用能存，但 `check-cast`、数组协变都没做）。
- 不校验数组的 component type：`[I` 之外的类型只是不拦，`[[I` 之类会被当成一维。
- 连续物理页会随运行时间碎片化：`arr_reset` 只在 `app start`/`run` 时整批还页，中途不回收。
- `MAX_ELEMS=4096` 是硬编码，真 APK 里一张 1080p 位图就要 200 万像素。

### 51.6 下一步

内存地基到此为止：对象堆、数组都是真内存，页帧池 32768 页里随时能看到占用。下一个瓶颈不在分配器，而在**语义**——`String` 只有 `StringBuilder` 三个方法、没有任何字符串拼接/比较/取长度，`android.graphics` 还是自研 Canvas。接下来该做 `String` 的方法族（`length`/`charAt`/`equals`/`concat`/`substring`），让 fixture 能写点像样的逻辑。

## 52. APK-15：String 方法族

§51 之后 `String` 是块砖：能拿到、能塞进 `StringBuilder`，但读不出长度、比不了、拼不了、切不了。这一节把 Java 里最常被调用的七个 `String` 方法补进内建表，并用一条 `Main.str()V` 把它们串起来验证。

### 52.1 动态字符串表扩容

原来的 `DYN: [[u8; 96]; 4]` 只够 `StringBuilder.toString()` 一次性的场景。改：

| 项 | 旧 | 新 |
| --- | --- | --- |
| `NDYN` | 4 | **16** |
| `DYN_CAP` | 96 | **128** |
| `SB` | `[u8; 128]` | `[u8; DYN_CAP]` |

关键是抽出一个公共登记函数 `dyn_push(b: &[u8]) -> Result<i32>`：长度超 `DYN_CAP` 报"字符串超过 128 字节"，槽用满报"动态字符串槽用尽（16 个）"，成功返回 `DYN_TAG + i`。`sb_freeze()` 直接改成 `dyn_push(&SB[..SB_LEN])`——因为 `DYN` 是独立缓冲区，不需要中转。另加 `str_concat(a, b)`：拼到临时 `[u8; DYN_CAP]` 后再 `dyn_push`，超长在拼接前就拦下。

这样 §44 的 `StringBuilder` 和本节的新方法走同一条出口，引用区间仍然是 `0x200..0x1_0000`，`str_of()` 一个入口全认。

### 52.2 七个方法

加在 `dex.rs` 的内建 `match m.class` 链里，位置在 `Ljava/lang/StringBuilder;` 之前：

| 方法 | 语义 | 返回 |
| --- | --- | --- |
| `length()I` | UTF-8 字节数（纯 ASCII 时等于字符数） | i32 |
| `charAt(I)I` | 第 i 个**字节**；越界报错 | i32（不是 char） |
| `equals(String)I` | 字节级相等 | 1 / 0 |
| `concat(String)String` | `str_concat` | 动态字符串引用 |
| `substring(II)String` | `[b, e)`，两端夹到合法区间，`b > e` 报错 | 动态字符串引用 |
| `indexOf(I)I` | 找第一个匹配字节，找不到返回 −1 | i32 |
| `valueOf(I)String` | `sb_reset` + `sb_push_int` + `sb_freeze` | 动态字符串引用 |

`valueOf` 有两个重载，靠 shorty 首字符区分：`valueOf(I)` 的 shorty 是 `"IL"`（首字符 `I`），`valueOf(String)` 是 `"LL"`，后者直接透传参数引用（`last = args[0]`），不额外占槽。

`charAt` 返回 i32 是刻意的简化：DEX 里 `C` 类型寄存器本质也是 32 位，只要不做 `check-cast`、不把结果当对象用，i32 完全够用。真实实现要处理 UTF-16 代理对，这里只承诺 ASCII 语义。

### 52.3 fixture：Main.str()V

13 版 `tools/mkdex.py` 新增 method 39（`Main.str()V`，55 code unit，regs=6），strings 表补 8 条（`" OS"`、`Aster`、`charAt`、`concat`、`equals`、`indexOf`、`length`、`substring`、`valueOf`、`IIL`、`IL`），proto 补 3 条（`(II)String` / `(String)String` / `(I)String`）。Main 的 class_data direct 7 → 8。

序列（每一步都打印，谁错就停在哪一行）：

```java

String t = s.substring(0, 5);        // Log.i -> "Aster"
```

`indexOf` 那行第一版注释写的是 6，实跑出来 7——`"Aster OS"` 里 `'S'` 确实在第 7 位（`A0 s1 t2 e3 r4 空格5 O6 S7`）。错的是我手算的注释，内核返回的 7 才是对的。断言按 7 落地。

### 52.5 限制

- 长度是字节数、`charAt` 是字节下标：非 ASCII 字符串（中文、emoji）拿到的数和 Java 对不上。
- `substring` 不做 UTF-8 边界校验，切在半个字符中间会得到非法序列（后续 `str_of` 会报"不是合法 UTF-8"，不会 panic）。
- 没有 `toUpperCase`/`toLowerCase`/`trim`/`startsWith`/`endsWith`/`replace`——真 APK 里这些调用频率不比 `length` 低。
- `equalsIgnoreCase`、`compareTo`、`hashCode` 都没有，`HashMap<String, …>` 仍然跑不起来。
- 16 槽 × 128 字节是固定的，一段循环里反复 `concat` 十几次就爆槽（`call_reset` 只在 `run`/`app start` 时清）。

### 52.6 下一步

字符串从"能存"到"能用"了，但**对象模型**还停在一层：没有 `ArrayList`，没有 `HashMap`，没有接口/多态分派（`invoke-interface` 根本没实现），也没有 `String[]` 之外的引用数组语义。APK-16 打算做 `invoke-interface` + 虚表，这是跑任何真实 APK 都绕不过的一步——现在 `Child`/`Base` 靠 `code_in_class` 上溯 4 层能跑，但一个类实现两个接口、同一方法名不同签名就立刻失效。

## 53. APK-16：接口与虚分派

§52 的 `invoke-virtual` 只按「方法名」找方法体。这在单继承下侥幸能跑，但一个类实现两个接口、两个接口又有同名不同签名的 `area()` 时，只比名字必然分派错。这一节把 `invoke-interface` 接上，并把方法匹配升级成 **(名字 + proto)** 双键。

### 53.1 三个改动

**① `MethodRef` 带 proto。** 原来只有 `class` / `name` / `shorty`，`shorty` 是 `"IIL"` 这种压扁串，不足以区分 `()` 和 `(I)`。补 `proto: u32`，直接给 `proto_idx`，比较时不解析参数类型列表，纯整数比较。

**② `code_by_sig(class_idx, name, proto)`。** 按 `class_idx`（不是描述符）定位 `class_def`，遍历 `direct_methods` + `virtual_methods`，`method(midx).name == name && .proto == proto` 才算命中。`code_off == 0` 视为「声明但没有方法体」（抽象方法），继续上溯。

**③ `code_iface(iface, name, proto, obj_class_idx)`。** 参数里那个 `iface` 其实不参与解析，只用来报错时说清楚是哪个接口：真正的落脚点是**对象的实际类**。从实际类开始沿 `superclass` 上溯最多 8 层，每层查 `code_by_sig`。对象引用 → 类索引靠 `obj_class_idx`：`heap_idx(v)` 拿槽地址，读 `sp+4` 的 `class_idx`（这正是 §50 页帧对象槽头的第二个字段）。

`new-instance` 里存的 `class_idx` 就是 `type_idx`，所以对象槽里天然记着「我是谁」，不需要额外维护类型标签。

opcode 侧只加一条：`0x72`（`invoke-interface`，35c 格式），并在通用分派处按 `(u & 0xff) == 0x72` 分支——接口走 `code_iface`，其余仍走 `code_of`。

### 53.2 顺手修掉的历史错位

`type_ids` 的写入顺序一直是 `S_BASE, S_BOOM, S_CHILD, S_RTE`，而常量是 `T_BASE=8, T_CHILD=9, T_RTE=10, T_BOOM=11`。也就是说 **APK-8 之后 `Child` 和 `Boom` 的描述符一直是对调的**：`child_def_pos` 写的是 `T_CHILD=9`，而 9 号实为 `"Lcom/aster/Boom;"`。

之所以没暴露，是因为内核所有解析都靠「描述符查 class_def」反查，`invoke-direct` 的 `m.class` 也来自同一张错表，两边一起错、内部自洽。改成与常量一致的顺序后行为完全不变，但 DEX 终于对得上名字了。

### 53.3 fixture：两个接口 + 一个实现类

```
interface Sh { int area(); int area(int k); }   // 同名不同签名
interface Tg { int area(); }                     // 与 Sh 同名
class Sq implements Sh, Tg {
    int area() { return 4; }
    int area(int k) { return k * k; }
}
```

`Main.poly()V`：
```java
Sh s = new Sq();
int a = s.area();      // 4  —— Sh.area()I
int b = s.area(3);     // 9  —— Sh.area(I)I，靠 proto 与上面那条区分
int c = ((Tg) s).area(); // 4 —— 换个接口、同名方法，仍落到 Sq.area()I
```

`Sh`/`Tg` 的 `class_data_off = 0`（接口只声明不实现，方法体在 `method_ids` 里但类里没有 class_data），`Sq` 写了 `interfaces_off` 指向 `[@Sh, @Tg]` 的 type_list，`superclass = 0xFFFFFFFF`（这份 fixture 没有 `Ljava/lang/Object;`）。

### 53.4 五个坑（全部真踩）

1. **`invoke-interface` 的 opcode 是 `0x72`，不是 `0x6e`。** 第一版 fixture 三条全写成 `0x6e`，于是全被当 `invoke-virtual` 处理，`code_of("LSh;")` 找不到 `class_data` → 上溯到 `MAX` → 报「已到根类」。查错时先打印了 `code_in_class` 的每一项，看到 `direct 45 = "poly" want "poly"` 相等却不返回，才反应过来根本没进 `0x72` 分支。
2. **35c 的 `argc` 在 unit0 的高 4 位。** 写 `0x0072` 是 `argc=0`，`args[0]` 从未填充，`obj_class_idx(0)` 立刻报「不是有效对象引用」。正确是 `0x1072`。
3. **实例方法的 `ins_size` 含 `this`。** 抽象方法 `area()I` 没有参数，但实现类的方法体是实例方法，`ins_size = 1`。写成 0 后 `exec` 的 `args.len() > ins_n` 校验直接拒掉（`argc=1` 却 `ins_n=0`）。
4. **`const/16` 的 A 是 8 位。** `const/16 v2, #3` 是 `0x0213`；写成 `0x1213` 后 A 读成 `0x12=18` → `regs[18]` 越界，**panic at dex.rs:904**。
5. **`0x1071` 手写成 `0x0171`。** 少了 `argc` 位，`Log.n` 的 `argc=0`、`args[0]` 恒 0，但 `exec` 全程不报错——三种方法都「跑完了」，只是数字全是 0。最后靠打印 `u=0x171` 才定位。

前四个当场就炸，第五个是**静默错误**，也是这轮最值得记的一条：解释器里 `argc` 算错不会崩，只会读到没被写过的寄存器，表现成「功能正常但结果全零」。

### 53.5 实拍

```
[DEX] 4
[DEX] 9
[DEX] 4
poly() 执行完（40 条指令），正常 return-void
```

`make test` **28 项 PASS**，新增：
```
[TEST] PASS 接口分派：同名不同签名按 proto 精确命中实现类
```

### 53.6 限制

- 不做接口合法性校验：对象类没实现那个接口也能跑通（只按 `name+proto` 找到同名方法就当命中），真 APK 里可能把 `Foo.area()` 错派到 `Bar.area()`。要严格就得读 `interfaces_off` 的 type_list 逐项核对。
- 没有 `invoke-interface-range`（`0x75`）、没有 default method（`invoke-interface` 落到接口自身的非抽象方法体）。
- 不支持接口继承、协变返回（`(name, proto)` 精确匹配，返回类型变了就找不到）。
- `code_of`（virtual/direct 路径）**仍只按名字匹配**，同一个类里两个同名不同参数的虚方法会撞——现有 fixture 里 `Sq` 就有两个 `area`，只是 `invoke-virtual` 那条路径没被 fixture 触发过。这是下一节要一并收掉的。

### 53.7 下一步

方法解析这块基本齐了，剩下的硬骨头在**容器**：`ArrayList`/`HashMap` 需要对象数组（`new-array [Lxxx;` 存引用）、`instanceof`（`0x20`）、`check-cast`（`0x1f`）、以及 `String.hashCode`。APK-17 打算先把 `code_of` 也升级成双键匹配，再补 `instanceof`/`check-cast` + 引用数组，为 `ArrayList` 铺路。

## §54 UI-9：GPU 真实呈现 + 手机端可输入可点击

这一节解决用户拿手机（Termux 里的 QEMU 前端）跑 Aster 时看到的三个现象：**画面一闪一闪、终端内容区经常一片空白、点不着也打不了字**。三个都是真实缺陷，不是"手机性能不够"。

### 54.1 三个根因

1. **ramfb 是"共享内存 + 主机随时采样"，没有帧的概念。** 内核每 70ms 调一次 `render_dashboard()`，而 `draw_desktop` 的第一件事是 `restore_wall(0,0,W,H)` 把整屏 3 MiB 擦回壁纸，然后画侧栏、再逐窗画。QEMU 的前端以 60Hz 从 `0x5000_0000` 采内存：**几乎每一帧都采在"壁纸已擦、窗口还没画"的中间态**，于是终端区是空的；偶尔采到完整帧，就闪一下。`fb::present()` 在 ramfb 路径下是空操作，等于放弃了"整帧原子呈现"这条唯一能救命的能力。
2. **`ZORD = [0,1,2]` 让终端窗口在最底层。** 终端（0）是最常用的窗口，却被"系统""网络"两块盖住右上角——手指点在红点上的其实是**上面那块窗口的标题栏**，所以"关不掉""点不动"。z 序在启动时定死，除非点到终端本体才会抬上来，而点到的是别的窗口，越点越乱。
3. **回显走的是串口，不是屏幕。** `shell::read_line` 用 `uart::putc(c)` 回显，只写 PL011；而 `uart::puts()`（`print!` 走的路径）才是"两份输出：屏幕 + 串口"。所以手机上敲字**屏幕毫无反应**——看起来就是"没法输入"。

### 54.2 改动

**走 virtio-gpu（DeviceID 16），一帧一次 flush**

`kernel/src/virtio_gpu.rs` 早就有 2D 资源路径（CREATE_2D → ATTACH_BACKING 挂 `0x5000_0000` 的 768 页 → TRANSFER_TO_HOST_2D → RESOURCE_FLUSH），但启动串从来没带 `-device virtio-gpu-device`，所以一直回落到 ramfb，这段代码等于没跑过。这次真正跑通，顺手修了三个 bug：

- **legacy 队列的 `used` 偏移**：legacy 规范把它放在 `desc` 之后按 4 KiB 对齐处（QSIZE=8 时正好 `+4096`），驱动原来写成 `+2048`，主机写 `+4096`、驱动读 `+2048`，永远等不到 → `create_2d 命令超时`。环缓冲同时从 4 KiB 扩到 8 KiB。
- **像素格式号**：QEMU 的 `virtio_gpu_formats` 里 `1 = B8G8R8A8_UNORM`、`3 = A8R8G8B8`。内核像素是 `0x00RRGGBB`、内存字节序 `B,G,R,X`，所以该填 **1**。填 3 时整屏偏绿（红蓝通道互换），第一版截图就是这个绿屏。
- **光标只 flush 小块**：`cursor.rs` 原来走 `present_rect`，和整屏 flush 交替，QEMU 侧 surface 出现"半新半旧"，文字重影。改成整屏 `present()`，重影消失。

启动参数从 `-device ramfb` 换成 `-global virtio-mmio.force-legacy=false -device virtio-gpu-device`（modern 队列用寄存器指定 desc/avail/used，比 legacy 的 PFN 推导少一层猜测）。`fb::init()` 的顺序不变：先试 GPU，失败才退 ramfb，所以老参数也还能跑。

**终端窗口置顶**

`ZORD` 初值 `[0,1,2]` → `[1,2,0]`。终端在最上层，点击必然命中终端；关窗、拖动、打字都落在"看得见的那块"上。

**屏幕软键盘（`kernel/src/kb.rs`，新文件）**

手机上 QEMU 前端送不进可靠 scancode，所以键盘画在 Aster 自己的界面里：

- 面板 500×244 贴在屏幕右下，5 行 ASCII（数字 / qwerty / asdfghjkl / zxcvbnm+DEL / SPACE+ENTER+-_+/+HIDE）；
- 键宽按内容算（SPACE、ENTER 双宽），每行居中，命中测试与绘制共用 `key_rect()`，不会错位；
- 点终端窗口的内容区（`y > w.y+44` 且没到底栏）自动弹出键盘，按 `HIDE` 收起；
- 字符直接进 `input` 的字符环（新增 `input::push_char`，与真键盘同一个 128 字节环），`read_line` 一行代码都不用改。

**标题栏热区放大**：`title_button_at` 从 `y ∈ [w.y+14, w.y+30]`、半径 ±8 改成 `y ∈ [w.y+8, w.y+38]`、半径 ±14 —— 32×30 的方块，手指能点中，视觉上的三色点大小不变。

**回显上屏**：`read_line` 的 `uart::putc` 全换成 `crate::print!`（屏幕 + 串口双写）；退格发 `\u{8} \u{8}`，`term::write` 新增 `\u{8}` 分支（光标退一格并抹白）——原来的 `term` 只认 `\n`/`\r`/`\t`。

- `build/gpu3.png`：GPU 接管（`[FB] virtio-gpu 2D 已接管：1024x768 resource #1 @0x50000000（合成后 flush 才上屏）`），颜色正确、文字清晰、无重影；对比 `build/kb2b.png`（ramfb，同一份 elf）正好是"终端区全黑 + 只有标题栏"的撕裂帧——用户截图里的那个画面。

### 54.4 限制

- 软键盘只有 ASCII，没有中文 IME（要另做候选串 + 拼音表，工作量和一套输入法编辑器相当）。
- 触摸仍是**相对位移**（`EV_REL`）语义：QEMU 前端的"触摸当鼠标"模式能用，但真正的绝对坐标设备（`virtio-tablet`）还没接，手指与光标在长距离上会漂。
- 键盘是浮层，会盖住终端下半部分（能 HIDE，但会反复开关）。
- 只有一块 resource、没有双缓冲：绘制仍在同一块内存上就地改，靠"画完才 flush"保证原子性；真正的前后台双缓冲 + 脏区合批还没做。
- GPU 路径要求 modern virtio-mmio（`force-legacy=false`）；legacy 那条路径这次没有回归验证（QEMU 默认就是 legacy，加了参数才 modern）。

### 54.5 下一步（UI-10）

1. 接 `virtio-tablet`（`EV_ABS` + `ABS_X/ABS_Y` + `BTN_TOUCH`），让手指坐标就是屏幕坐标，去掉漂移；
2. 双缓冲：`FB_BACK` 另一块 3 MiB，画完 `memcpy` 到前台再一次 flush，同时按脏区合批，省掉每帧 3 MiB 的 transfer；
3. 软键盘加"最近命令"行（把 `↑` 历史做成三个可点的 chip），手机上少打字；
4. 窗口开合过渡（缩放 + 淡入），补上 UI-8 欠的动效。

## §55 UI-10：手机端少打字（一键命令 + 历史键）

§54 把键盘放上屏之后，新的痛点是**打得太多**：一行 `dex big` 要点八下。这一节只做"少打字"，不动渲染。

### 55.1 一键命令行

软键盘顶部加一行 chip（`kb.rs::CHIPS`），点一下就把**整条命令连回车**塞进字符环：

```rust
for b in crate::kb::CHIPS[idx].as_bytes() {
    input::push_char(*b);
}
input::push_char(b'\r');
```

`read_line` 一收到 `\r` 就返回，所以 chip 与"手打 + 回车"在 shell 眼里完全一样。当前七条：`help` / `info` / `dex run` / `dex big` / `apk` / `wins` / `clear`。chip 宽度按 `fb::text_len_ui()` 算，命中测试与绘制共用 `chip_rect()`，不会错位。

### 55.2 历史键 UP / DN

`shell.rs` 新增 `HIST: [[u8; 64]; 8]` 环形缓冲（`HIST_N` 总条数、`HIST_AT` 当前浏览位置，1..=HIST_N 表示第几条，`HIST_N` 表示新的空行）。每条非空命令执行前写入。

键盘上的 UP/DN 不是 ASCII，用两个**伪键**传递：`0x90` 上一条、`0x91` 下一条。`read_line` 在可打印字符分支之前先匹配它们，做三件事：按 `n` 个 `\u{8} \u{8}` 擦掉当前行、把历史条目回填进 `buf`、逐字节回显。这样输入缓冲与屏幕内容始终一致，不需要额外保存"当前行副本"。

伪键选 0x90/0x91 而不是真键码，是因为字符环只有 `u8` 且 `read_line` 没有"键事件"通道；代价是不能在命令行里输入这两个字节（本来也无意义）。

### 55.3 现场

- `build/chip1.png`：键盘顶部七条 chip，键盘整体高度 270px（含 chip 行），仍在屏幕下方不压住底栏。
- `build/chip2.png`：点 `dex big` → 直接出现 `$ dex big` → `[DEX] 2096128` / `big ok` / `28690 条指令`，全程零键盘敲击。
- `build/hist1.png`：点 UP 后命令行回填 `sim click 500 400`（上一条历史），文本与缓冲一致。
- `make test` **28 PASS / 0 FAIL**。

### 55.4 限制与下一步

- chip 是写死的七条，不跟着上下文变（真正的做法是拿 `help` 的命令表动态生成 + 按使用频率排序）。
- 历史只有 8 条、每条 64 字节，没做"前缀过滤"（`de<TAB>` 补全）。
- 绝对坐标触摸仍然没解：QEMU 6.2 的 `virt` 机器**没有** `virtio-tablet`（`-device help` 里查不到），内核也没有 USB 控制器路径可用，所以"手指直接定位"只能等真机（树莓派 + USB 触摸屏）那条线，或者 QEMU 前端自己把触摸翻成绝对坐标。
- 双缓冲 / 脏区合批仍未做：现在每帧全屏 flush 3 MiB，在 QEMU 里够用（一次 transfer 约几毫秒），但真机上会明显吃带宽。

## §56 UI-11：窗口三态闭环 + dock 格子 + 双缓冲

§54/§55 解决了"看得见、打得进字"，但窗口管理还是残的：**最小化和关闭走的是同一个函数**（`minimize_win` 直接调 `close_win`），关掉的窗口再也回不来（只能重启），最大化之后左侧栏被盖住、连"还原"都点不到。这一节把三颗按钮补成真正的三态闭环，并顺手把 §55.4 欠的双缓冲落地。

### 56.1 窗口三态

`WINS[i].open` 之外的第二个布尔 `MINED[i]`，两者组合出三态：

| 状态 | open | MINED | 语义 |
|---|---|---|---|
| 0 关闭 | false | false | 状态清空，dock 上不占格，要从侧栏图标重新打开 |
| 1 在桌面 | true | — | 正常显示，可拖动/最大化 |
| 2 最小化 | false | true | 从桌面消失但还活着，dock 上占一格暗色格子 |

`close_win` 清两个标志，`minimize_win` 只把 `open` 放下并保留 `MINED`，`show_win`（侧栏/dock 都走它）两个一起恢复。窗口从桌面消失后焦点自动交给"还在桌面上的最上层窗口"——两个函数共用的那段倒序扫描没有改动。

**最小化后窗口仍然可以最大化**：`MAXED` 只在 `close_win` 里清，`minimize → dock 点回` 之后还是最大化状态。

### 56.2 dock 变成真正的任务栏

原来底栏是静态画的两块（"开始"+"终端"），现在只画底板和"开始"按钮，窗口格子交给 `draw_dock_items()` 每帧画：

- 三格 72×30，起点 x=116，间隔 4，底板加宽到 360；
- 打开且聚焦 → 蓝底 + 蓝框；打开但没聚焦 → 灰底 + 细框；最小化 → 更暗的底 + 文字降为 DIM；关闭 → 不画；
- `dock_hit()` 与绘制共用同一套坐标，命中即"点格子"。

点的行为按"任务栏惯例"：点已聚焦的格子 = 最小化；点其它（含最小化的）= 打开并抬升。侧栏图标同样的规则（点自己已激活的图标就收起来），所以手机上两种入口都能开关窗口。

### 56.3 最大化让出侧栏

`toggle_max` 原先把窗口铺到 (16,56)–(W-16,H-96)，把 104px 宽的侧栏整个盖住 —— 最大化之后既点不到侧栏，也点不到自己的"还原"绿点（绿点在窗口右上，倒还在，但侧栏导航没了）。现在改成 `x=112, y=52, w=W-128, h=H-52-88`：左侧栏完整保留，底部 dock 也留出来。

### 56.4 双缓冲

`fb::init` 先向页帧分配器要 768 页（3 MiB）：

```rust
let npages = ((FB_W * FB_H * 4) as usize).div_ceil(4096);
let draw_base = alloc_back(FB_PHYS);   // BACK_PA / REAL_PA / GPU_MODE 三件套
```

绘制全部写 `BACK_PA`，`present()` 按模式分两条路：

- **GPU**：`virtio_gpu::init(draw_base, …)` 直接把 resource 的 backing 挂在后台缓冲上，`TRANSFER_TO_HOST_2D` 从 RAM 读 → **一次 memcpy 都不做**，只有一次 transfer + flush；
- **ramfb / mailbox**：`present()` 里整帧 `copy_nonoverlapping(BACK_PA → REAL_PA)`，让 QEMU/VideoCore 采样的是"已经画完的整帧"。

池子不够时 `alloc_back` 退化成单缓冲（`BACK_PA=0`），一切照旧能跑。代价是常驻 3 MiB（测试里页帧从 10 页变 778 页，`make test` 的断言同步改了）。

**脏区合批没做**，原因写清楚：现在每一次重绘都是整屏级（`restore_wall(0,0,W,H)` + 逐窗），脏区永远是全屏，合批收益为零。等以后改成"只重画变化的窗口/终端行"时再一起上。

- `build/reopen2.png`：点红点关闭（dock 上"终端"格消失）→ 点侧栏"终端"图标 → 重新打开；
- `build/kbmin.png`：键盘弹着时点黄点 → 窗口最小化 + 键盘一并收起（不然自己挡 dock）；

### 56.6 限制

- 没有开合过渡动画：窗口是"瞬间出现/消失"，§54.5 提到的缩放淡入还没写。
- 最小化只有 dock 一格位置，没有缩略图/预览。

## §57 有线的真与无线的实（NET-2 / TZ-1 / PKG-1b / PERF-2）

### 57.1 网络：从"未找到设备"到 HTTP 200

上一轮的串口里一直有 `[NET] 未找到 virtio-net 设备`，原因不在驱动而在**命令行没带设备**。加上

```
-netdev user,id=n0,hostfwd=tcp::8088-:80 -device virtio-net-device,netdev=n0
```

之后 `net` 立刻打印 `virtio-net 已就绪 MAC 52:54:00:12:34:56 IP 10.0.2.15/24 GW 10.0.2.2 HTTP :80`。宿主侧 `urllib` 请求 `http://127.0.0.1:8088/` 拿到 **HTTP 200**，正文是内核里手写的 HTML（`<title>Aster · 星芒</title>`），不是转发、不是回显，是 `net.rs` 自己的 TCP 状态机收 SYN、回 SYN-ACK、收 GET、拼响应头。

两个坑值得记：

1. **8080 端口被宿主上的 caddy 占着**，hostfwd 绑不上会静默失败，换 8088。
2. 设备名是 `virtio-net-device`（MMIO 版），不是 `virtio-net-pci`；`-global virtio-mmio.force-legacy=false` 必须和它一起给，否则 legacy 队列寄存器偏移对不上，收包全零。

现在的 IP 是**写死**的 `10.0.2.15/24`、网关 `10.0.2.2` —— 这是 QEMU user 模式的固定约定，正好省掉 DHCP。真要上真机或桥接网络，DHCP 客户端是下一步。

### 57.2 性能：把最贵的那一步按需化

`perf` 原来报 `整桌 38 ms / 壁纸 3 / 侧栏 0 / 窗口 38`。窗口 38 ms 几乎全在投影：每个窗口四层大矩形做 alpha 混合，1024×768 上就是几百万次读写。

做法不是"把阴影做便宜"，而是**把阴影变得不常画**：

- `SHADOW_UNTIL` 记一个绝对毫秒时间戳，`ask_shadow()` 把它推到 `now + 150ms`。
- `draw_desktop` 末尾原来是 `draw_all()`（永远带阴影），改成 `draw_all_ex(shadow_wanted())`。
- `raise / move_window / close_win / minimize_win / toggle_max / show_win` 六处各加一行 `ask_shadow()`。

语义上很自然：**窗口几何刚变过的那一小段时间要阴影，静止时不要**。拖窗口时每帧都 `ask_shadow`，所以拖动过程中阴影一直在；松手 150 ms 后自动消失，此时终端滚字、光标闪烁这些高频帧走无阴影路径。

复测 `整桌 17 / 壁纸 4 / 窗口 17`，再测 `16 / 4 / 16` —— **2.3 倍**，且静止帧不再有"每次重画都在做无用混合"的浪费。

还剩两块肉：

| 项 | 现在 | 该怎么做 |
|---|---|---|
| 壁纸 4 ms | 每帧 `restore_wall(0,0,W,H)` 整屏 3 MiB memcpy | 壁纸本来就静态，只需要在窗口露出区域恢复；做脏矩形就行 |
| 窗口 16 ms | 三个窗口全量重画，包括没变的系统/网络窗 | 每窗一个 `DIRTY` 矩形，只重画和上次不同的部分；终端按行脏标记 |

这两项是 PERF-3 的内容，等 UI 再稳一版做。

### 57.3 时区：编译期常量，不给用户改错的机会

`rtc.rs` 里三个常量：

```rust
pub const TZ_NAME: &str = "Asia/Shanghai (CST)";
pub const TZ_OFFSET_HOURS: i32 = 8;
pub const CST_OFFSET: u64 = 8 * 3600;
```

PL031 给的是 UTC 秒，`local()` 一律 `+ CST_OFFSET`，`md()` 用自写的儒略日换算出年月日。`date` 打印带时区名，`tz` 专门自查：

```
$ tz
  时区      : Asia/Shanghai (CST)
  UTC 偏移  : +8
  夏令时    : 无（中国 1991 年后已取消）
  改法      : 改 kernel/src/rtc.rs 的 TZ_OFFSET_HOURS，重编即生效
```

不做"用户可配置时区"是刻意的：这也是用户的硬要求（固定上海），而且配置项要落到 AsterFS、要有时区库、要有 UI，收益极低。

### 57.4 包管理：先是格式，再是网络

`ASEPKG1` 包格式，144 字节头：

| 偏移 | 长度 | 内容 |
|---|---|---|
| 0 | 8 | 魔数 `ASEPKG1\0` |
| 8 | 16 | 包名（ASCII，补零） |
| 24 | 12 | 版本号 |
| 36 | 4 | 包体长度（LE） |
| 40 | 4 | CRC32 |
| 44 | 52 | 一行描述 |
| 96 | 48 | 包体（当前是占位） |

`tools/mkpkg.py` 生成四个索引项：`python3 3.12.4`、`gcc 13.2`、`git 2.43`、`gh 2.40`。`shell.rs` 里 `PKGS: [PkgEnt; 4]` 用 `include_bytes!` 把 `.ase` 编进内核，`PKG_ON[4]` 记安装状态。

`pkg` 四个子命令：

- `pkg list` — 索引表，`[已装]` / `[可装]`
- `pkg info <名>` — 版本、包体大小、落盘路径、CRC
- `pkg install <名>` — `vfs::open(path, true)` 建文件 → `vfs::write` 写头 → `close`，落进 AsterFS，置 `PKG_ON`
- `pkg remove <名>` — 只清标志（AsterFS v0 没有 unlink）

命令分派踩过一次坑：原来写成 `"pkg" => ...` 整行匹配，`pkg list` 落到"未知命令"。改成前缀分支 `l if l == "pkg" || l.starts_with("pkg ")`，`tz` 同样处理。

**边界要说清**：现在装的是 144 字节的占位包，能从索引里"装"进文件系统，但里面没有真程序。真装 Python 需要 ① HTTP 客户端去拉（P6-4）② 解包 ③ ELF/脚本加载器（阶段四）④ 依赖解析。`pkg` 现在证明的是**格式、索引、落盘三件事对了**。

### 57.5 无线：没有硬件，就不写在纸上

`wifi` 命令的输出是本节的诚实版：

```
$ wifi
  无线      : 硬件层没有 802.11 适配器，WIFI-1 未开工
  QEMU virt : 没有 SDIO / PCIe 无线网卡可枚举
  树莓派    : BCM43438 挂在 SDIO 上，需要先做 SDHCI(EMMC) 驱动
  现实路径  : SDHCI → SDIO 枚举 → 固件上传 → WPA2 握手（四步，都是硬骨头）
  眼下替代  : virtio-net 当有线用，QEMU 的 -netdev user 自带上游 NAT
```

为什么不先写个假的 `wifi connect`：QEMU virt 机器根本没有 802.11 设备可枚举，写出来的命令只能打印"已连接"，那是欺骗。树莓派的 BCM43438 走 SDIO，而 SDHCI 驱动本身就是 BOARD-4 的活儿，还没开工 —— 顺序上必须先有 EMMC/SDHCI，才谈得上 SDIO 枚举，才谈得上把 `.bin` 固件塞进芯片，才谈得上四次 WPA2 握手。

所以 WIFI-1 的任务拆成四步，每步都能独立验收：

1. **SDHCI**：CMD0/8/41/2/3/7/16，PIO 模式读扇区，接进 `disk`
2. **SDIO 枚举**：CMD52/CMD53，认出 BCM43438 的 vendor/device
3. **固件**：把 `brcmfmac43438.bin` 分块写到芯片的 download 寄存器，等它切到固件模式
4. **WPA2**：四次握手（EAPOL）+ CCMP，密钥派生用自研 SHA-256

这四步做完才有一行 `wifi connect SSID PASS`。现在写的是第 0 步：让人知道差多远。

### 58.1 包索引从"手写 4 个"变成"脚本生成 80 个"

### 58.2 第二刀性能：把"每帧都要做的事"变成"变了才做"

上一刀（PERF-2）砍的是阴影：只在窗口动过之后 150 ms 画。这一刀砍两处：

**一、壁纸惰性恢复。** `draw_desktop` 里原来无条件 `restore_wall_gaps()` 整屏搬 3 MiB。其实静止帧上壁纸像素本来就是对的 —— 唯一会变的是顶栏时钟。于是：

```rust
if take_wall() || minute_changed { restore_wall_gaps(); }
```

`ask_wall()` 由这几个时机触发：`win_touch_all()`（窗口开关/移动/最大化/焦点变化）、`kb::set_open()`（软键盘开合）、`ui::tick` 里 `want`（鼠标点击/拖动/悬停）。时钟走 `rtc::hm()` 的分钟数，跳格才重擦。

**二、终端行级增量。** `term.rs` 加 `D0/D1/ALL` 记录脏行范围：`put` 标当前行、`newline` 标新旧两行、滚动 `ALL=true`。`fb::term_patch()` 只擦、只画这几行，标题栏和圆角面板留上一帧的。

这里有一个**必须记住的约束**：增量渲染要求终端是屏幕上唯一窗口。因为窗口按下标一层层整画，下层窗口的整画会盖掉终端像素，而补脏行补不回整块矩形 —— 多窗口时 z 序会错（实测确实错了：系统窗压到了终端上面）。所以代码里加了 `others_open` 判断，**只要还有别的窗口打开就走整窗重画**。

实测：

| 场景 | 整桌 | 壁纸 | 窗口 |
|---|---|---|---|
| 三窗口 | 18–20 ms | 0 | 18–20 |
| 只留终端（`win off 1` `win off 2`） | **0 ms** | 0 | **0** |

"整桌 0 ms"不是没画，是这一帧只补了 perf 命令刚打出来的两行。

### 58.3 三窗口为什么还停在 18 ms

因为三个窗口互相重叠，整画顺序决定像素归属，任何"局部重画"都会打破它。真正的解法是**离屏合成**：

1. 每个窗口一块自己的层（`Wb × Hh × 4`，最大的最大化终端 896×628 ≈ 2.2 MiB，三块约 5 MiB，页帧池够）。
2. 窗口内容只在自己的层上画脏区，层内像素永远自洽。
3. 每帧按 ZORD 顺序把各层 blit 到后台缓冲：3 个矩形约 2.3 MB memcpy，~2–3 ms，加上脏区绘制，目标 4–5 ms。

这条路要求绘制函数支持"当前目标切换"（`fb()` 返回可替换的 `Fb { base, stride, w, h }` + 原点偏移），改动集中在 `fb.rs` 一处，但要逐个验证圆角、阴影、文字在层坐标下的裁剪。列为 **PERF-4**，下一轮做。

### 58.4 当前这份快照的边界

- 包：80 个索引项全部是 144 字节占位包体，能查、能装、能落盘；装进去的不是可执行程序。
- 网络：有线通（HTTP 200 实测），IP 写死 10.0.2.15；无线没硬件路径；DHCP/DNS 是 NET-4。
- 性能：单窗口已经"零成本"，三窗口 18 ms；`make test` 36 项断言。

## 59. 内置浏览器（P6-5）：把别人的 HTML 排成自己屏幕上的行

浏览器窗口是第四个窗口，`ZORD` 最上层。它不做完整引擎——不做 CSS 层叠、不做表格布局、不解码图片、不跑 JS。它只保证一件事：**把真实 HTML 排成能读的字**，整齐、能滚、链接能点。

### 59.1 分词器（`kernel/src/html.rs`）

状态机逐字节扫 `src`，不建 DOM，直接把结果压成定长行：

- 上限 `MAX_LINES=320`、`CELLS=96`、`MAXW=76`（**半角单位**：ASCII 记 1，汉字记 2，折行按此累加）
- `Line { cells:[u16;96], len, kind, indent, href:[u8;72] }`，`kind` 决定行级样式：0 正文 / 1 h1 / 2 h2 / 3 h3 / 4 链接 / 5 代码 / 6 引用 / 7 分隔线 / 8 空行 / 9 图片占位
- 认的标签：`p div h1 h2 h3 li ul ol br hr pre code a img title meta`；`script style` 整段跳过，注释跳过
- `CUR_CLOSED` 决定"要不要开新行"：块级开始先 `flush()` 收行，字符进来时若行已关就 `push_line()` 开新行——**行在开的那一刻把当前 href 拷进去**，这是行级链接能被点击的关键
- `<a>` 到达时先 `flush()` 再设 `CUR_KIND=4`，让链接独立成行，行级样式才落得上
- 实体：`&amp; &lt; &gt; &quot; &nbsp;`；相对 href 拼 `base` 的 `scheme://host`

### 59.2 行 → 像素（`kernel/src/web.rs`）

`row_h(kind)`：h1 34 / h2 26 / 分隔线 18 / 空行 10 / 其余 21。`relayout()` 把高度累加成 `TOPS[]`，`TOTAL` 就是整页高，`max_scroll = TOTAL - VIEW_H`。

绘制：内容区顶上是 38 px 地址栏（"地址 " + URL + 状态点 + 右对齐页面标题）；地址栏底下按 `TOPS[i] - SCROLL` 逐行画，滚出视口的行直接跳过。h1 用 `scale=2` 加强调下划线，h2 强调色加 18 px 装饰线，链接强调色加下划线，代码绿，`img` 显示 `[img]` 占位。右侧画滚动条：轨道 + 按 `scroll/max` 换算的滑块。

### 59.3 取页

- `open_home()` 解析编译期 `include_bytes!("../../assets/web/home.html")`，地址栏 `aster://home`，断网也能开
- `open_addr("ip:port/path")`：没有 DNS，只认 IP + 端口 → `net::http_get` → 跳过 `\r\n\r\n` 取 body → 重新分词排版；失败（未就绪/ARP 失败/连不上/超 16 KiB）走 `err_page()`，把原因写在页面上，不空屏
- 域名会直接报错并把原因指到 NET-4（DHCP+DNS 还没做）

### 59.4 命中与滚动

- `link_at(x,y,内容起点,窗口底)` 反查：`ry = y - (内容起点+38) + SCROLL` → 在 `TOPS` 里二分线性找行 → 行 href 非空返回静态串，`ui` 侧直接 `open_addr`
- 内容区按住拖动：`WSC/WSC_Y0/WSC_S0` 记按下点与当时的 `scroll`，手指位移 ×1.6 换成滚动量（`scroll_to` 会 clamp），松手结束。点链接优先于拖动
- 命令侧：`web` / `web home` / `web <ip:port/path>` / `web scroll up|down|top|<数字>`

### 59.5 实测

- `web`：内置首页 28 行，h1/h2/分隔线/圆点列表/段落折行/地址栏/状态点/滚动条全部正常
- 点首页里的链接：地址栏从 `aster://home` 变成 `http://10.0.2.2:8000/home.html`，从宿主 `python -m http.server` 真拉一次再排版
- `sim drag 500 420 500 260`：内容上滚 256 px，滚动条同步下移
- `make test` 增加两条断言（首页行数、滚动位置）

### 59.6 诚实边界

没有 CSS 层叠、没有表格布局、没有图片解码（只画 `[img]` + alt）、没有 JS、没有表单输入、没有 TLS（所以只能 `http://`）、只认 IP+端口（域名等 NET-4）、单页无历史栈（点链接不产生"后退"）、`MAX_LINES=320` 行封顶、80 列宽按窗宽固定（不随窗口拉伸重排）。

## 60. 图片解码（IMG-1）：浏览器终于能看图

`img` 的占位符换成了真像素。解码器在 `kernel/src/img.rs`，只认两种格式，但两种都不靠外部库。

### 60.1 支持面

- **BMP**：24/32bpp、`BI_RGB` 无压缩、bottom-up 与 top-down（高度为负）都认
- **PNG**：8bit、color type 2(RGB) / 6(RGBA)、非隔行；多 IDAT 只取连续第一段；zlib 头两字节剥掉后直接喂给 `inflate`（APK 那条 DEFLATE 复用）
- 反滤波 Sub / Up / Average / Paeth 全做，Paeth 用整数差比
- **不做**：调色板、16bit、隔行、Gamma/ICC、alpha 混合（`a<128` 直接跳过露出底色）
- 源图上限 256×256；解出来先落 RGBA，再按整数倍缩小到 160×160（只缩不放，避免插值糊字）

### 60.2 三块大缓冲不进 .bss

一开始把三个数组（源图 256 KiB、解压临时 257 KiB、成品 100 KiB）写成 `static mut [..]`，立刻踩到坑：

```
relocation R_AARCH64_ADR_PREL_LO21 out of range: 1205492
references 'ASTER_USER_CTX'
```

BSS 一变大，C 那边 `&ASTER_USER_CTX` 这种 `ADR` 相对取址就超出 ±1 MiB。改法是把三块缓冲从页帧分配器懒要（`frame::alloc_pages`），内核 `.bss` 回到原位。实测浏览器开图后页帧从 768 → 922（多 154 页 ≈ 616 KiB）。

### 60.3 两种字节序

BMP 是小端，PNG 是大端（chunk 长度、宽高全是大端）。第一版统一用 BMP 的小端读，PNG 直接报"没有 IDAT"—— chunk 长度读反了，指针一步就飞了。现在 `rd_u32`（小端，BMP 用）与 `rd_be32`（大端，PNG 用）分开。

### 60.4 页面里怎么用

`<img src=...>` 那一行 `kind=9`，`src` 存进行里的 `href`（72 字节）。打开页面时 `load_images()` 扫第一张图：

- `aster://...` → 内置 `assets/web/logo.png`（`include_bytes!`，离线可用）
- `http://ip:port/path` → `net::http_get` 取 body 字节 → 解码
- 其它/失败 → 保留 `[img] alt` 占位，不空行

行高由图片高度决定（`row_h(9) = img 高 + 14`），所以排版跟着图走。

### 60.5 实测

内置首页 `<img src="aster://home/logo.png">` 解出 120×120 的星芒徽标（深蓝径向渐变底 + 8 条白色射线），显示正常；页面 30 行；`make test` 断言首页行数。

## 61. 用户与权限（SEC-1）

系统原来只有一个隐含身份。现在有用户表、有 inode 权限位、有门。

### 61.1 模型

- 用户：`root`(0) / `aster`(1000，默认) / `guest`(1001)，`useradd` 最多加到 8 个，名字只允许小写字母/数字/下划线
- 权限：Unix 三位 rwx（owner/group/other），这一版只看 **owner 位** 与 **other 位**，group 位留着
- 判定：`uid 0` 全通；否则 `owner == 当前 uid` 看 owner 位，别人看 other 位
- 门：切到 root 必须 EXTREME 已解锁（`ex` 之后），普通用户随便切；`chown` 要 root 或 EXTREME；`useradd` 同理

### 61.2 inode 布局（64 字节）

`typ` 在 +0，**`mode` 在 +2**（这个位置原来写 0，正好空着），`size` +4，`parent` +8，`mtime` +12，10 个直接块 +16..56，**`uid` 在 +56**。新文件 `mode=0644`、`owner=当前 uid`；重写已有文件沿用它原来的 mode 与 owner。

### 61.3 三道门

| 位置 | 检查 |
|---|---|
| `afs::read_file` | 读位（owner/other） |
| `afs::write_file` | 覆盖已有文件前查写位 |
| `vfs::open(wr)` | 写打开再查一次（EACCES -13） |

`chmod <八进制> <文件>`、`chown <用户|uid> <文件>`、`ls -l`（`-rw-r--r--  5  aster  a.txt`）、`whoami`/`id`、`users`、`su`。

### 61.4 顺手挖出来的老坑

`ls -l` 一开始文件名是空的、size 0、mode 644。根因不是权限：`inode_read` 与目录遍历共用同一张 `CELL` 缓冲，两次 `buf()` 返回同一个 `&mut [u8;4096]`——**别名 UB**，编译器认为内容没变，读回的就是旧值。表现是"有时对有时错"，单独 `stat` 永远对。

修法是给 inode 读写单独一张 `CELL3`。这个坑在 AsterFS 里存在很久（只是以前没人嵌套读），现在从根上分开了。

### 61.5 实测

```
$ whoami
  aster  uid=1000 gid=1000  权限（非 root：看 owner 位，别人看 other 位）
$ ls -l
  -rw-r--r--       5  aster     a.txt
  -rw-r-----       6  aster     b.txt
$ su guest
  → guest (uid 1001)
$ cat b.txt
  没有读权限（owner 不是你）
$ wr b.txt hack
  没有写权限（这个文件不是你的）
$ cat a.txt
  hello
$ su root
  切 root 要先解开 EXTREME（ex 命令）
```

`make test` 38 项断言，新增：用户身份、用户表、gid 一一对应、`passwd` 用户库命令、root 要 EXTREME。

### 61.6 边界

没有 setuid、没有 ACL、没有密码（`su` 靠 EXTREME 而不是口令）、（组与 `/etc/passwd` 落盘已在 §62 补齐）。扩展属性与 xattr 都没有。

## 62. PERF-4 离屏合成 · SEC-2 组与目录权限

### 62.1 为什么之前三窗口要 18 ms

旧路径是"重叠就整画"：两个窗口一叠，下面那个的任意一块都可能是脏的，只能把它整个重画一遍（rounded_rect + 标题 + 正文），相当于每次交互都在重铺桌面。壁纸惰性和终端行级增量（PERF-3）已经把单窗口降到 0–1 ms，但只要开第二个窗口，整桌又回到 18–20 ms。

### 62.2 每窗口一块离屏层

`fb.rs` 换成"先画到层里，再按 z 序贴回屏幕"：

- `set_layer(i) / clear_layer() / in_layer()`，`put()` 与 `get()` 层优先：层内坐标越界直接丢弃，不会踩到别人的像素；
- `px / read_px / write_px / fill_rect / blend_px` 全部改走 `put/get`，于是 `blend_px` 在层内读改写同一块内存（阴影/半透明不再穿透层）；
- `layer_prepare(i, w, h)` 按页向页帧池要内存（尺寸变了就逐页释放再重新要），`LP_PA/LP_W/LP_H/LP_OK/LP_GEO` 记状态；
- `blit_layer(i)` 把层裁剪到屏幕后用 `copy_nonoverlapping` 整行贴回，`compose_layers()` 按 `ZORD` 顺序逐层贴。

`draw_one_layer(i)` 的顺序是：阴影先直接画在屏幕（阴影属于桌面，不属于层）、然后 `set_layer` → 圆角底 → 标题 → 正文 → `clear_layer` → `layer_mark`。

`draw_all_ex` 现在是两条路：只有一个窗口且无阴影时仍走原来的快速路径（`layer_invalidate(0)` + `term_patch()`，1 ms）；否则按 z 序判断每个窗口 `shadow || take_full || !layer_ok || layer_geo_changed` 是否需要重画，最后统一 `compose_layers()`。

实测：`win on 1` + `win on 2` + `perf` → **整桌 2 ms**，单窗 1 ms；页帧 1662 / 32768（四块层约 740 页）。键盘、系统窗面板、浏览器窗口在同一张截图里全部正常，没有互相擦除的残影。

### 62.3 组：gid 进 inode 与用户表

- `auth::User { name, uid, gid }`，`gid_of(uid)` 默认等于 uid（root=0、aster=1000、guest=1001）；
- `can(mode, owner, gid, want)` 变成三段判断：root 全通 → owner 位 → **同 gid 走组位** → other 位；
- AsterFS v0 的 Inode 补了 `gid`（偏移 +58，`+60..64` 清零），`meta()` 返回 `(mode, uid, gid)`，`set_meta(name, mode, uid, gid)` 四参，`read_file/write_file` 的权限检查都带上 gid；
- 新命令 `chgrp <gid> <文件>`（要 root 或 EXTREME），`chown` 顺带把 gid 跟着新 owner 走，`whoami` / `users` / `ls -l` 都显示组。

组位实证（一次跑完）：

```
$ wr b.txt aster-secret      → 12 字节
$ chmod 640 b.txt            → b.txt → -rw-r-----
$ chgrp 1001 b.txt           → b.txt → gid 1001
$ su guest                   → guest (uid 1001)
$ cat b.txt                  → aster-secret        ← 同组，组位 r 生效
$ su aster
$ chgrp 1000 b.txt           → b.txt → gid 1000
$ su guest
$ cat b.txt                  → 没有读权限（owner 不是你）  ← 组不对，other 位没 r
```

### 62.4 目录权限与 passwd 落盘

- `format()` 建根目录 inode 时写 `mode=0o755`、`uid=1000`、`gid=1000`；
- `list()` 开头按根 inode 的 mode/uid/gid 查读位，没读位就报"没有权限列这个目录"（不再只看文件 inode）；
- 用户库落盘：`auth::serialize/parse` 走文本行 `name:uid:gid`，`mkfs` 成功后自动写一份 `passwd`（3 个用户 55 字节），`useradd` 之后自动写回，开机 `auth::load_from_disk()` 从 `passwd` 恢复（读不到就保持内置三个）；
- 新增 `passwd` 命令：打印内存用户库（含 gid）并同步到磁盘。

```
$ mkfs                       → 用户库: passwd 已写入（3 个用户）
$ ls -l                      → （空目录）
$ useradd bob                → 已加用户 bob (uid 1003) / 已写入 passwd
$ ls -l                      → -rw-r--r--  55  aster  passwd
$ cat passwd                 → root:0:0 / aster:1000:1000 / guest:1001:1001 / bob:1003:1003
```

`passwd` 用的是普通 644 文件和普通读写路径（没有单独的"系统文件"特判），所以 `su guest` 之后 `cat passwd` 照样能读——这正是 `/etc/passwd` 在世界可读语义下的行为。

### 62.5 边界

setuid/setgid 位还没做（`can` 不认 0o4000/0o2000），组只有"主组"一个（没有附加组），`chgrp` 要 root/EXTREME 而不能"自己文件的组随便改"，`passwd` 也没有口令字段（`su` 仍靠 EXTREME 而不是密码）。
